1  ·  WHAT A CONTAINER ACTUALLY IS — AND WHAT DOCKER IS WITHIN THAT start here — containers are not lightweight virtual machines, and the licensing question has a precise answer
The definition
A container is a normal Linux process with a restricted view of the system. There is no virtualisation and no guest operating system — the kernel is shared with the host. Two kernel features do all the work.
NamespacesIsolation — what the process can see. Separate views of processes, network interfaces, mounts, hostname, users and inter-process communication. The process genuinely believes it is alone
cgroupsLimits — what the process can use. CPU, memory, block I/O and process count, enforced by the kernel
So “a container is a lightweight VM” is wrong in the way that matters. A VM has its own kernel and a hypervisor boundary. A container is a process sharing your kernel — which is why it starts in milliseconds, why the isolation is weaker, and why a kernel exploit from inside a container reaches the host. This distinction drives every security decision on this sheet.
What Docker adds on top: an image format and a build system, a daemon that manages lifecycle, a registry protocol for distribution, and a command line that makes all three approachable. The image format is the durable contribution — it is now the OCI standard, and it is why an image built with Docker runs on containerd, CRI-O, Podman or Kubernetes without change.
STAFF The licensing question, answered precisely — because it is very often stated wrongly. Docker Desktop requires a paid subscription for organisations with 250 or more employees or 10 million dollars or more in annual revenue. It remains free for personal use, education, non-commercial open source and smaller companies.
Docker Engine and the Moby project are Apache 2.0 with no such restriction. The fee attaches to the desktop application — the graphical interface and its helper virtual machine — not to the container runtime. “Docker is no longer free” conflates two different products, and on Linux servers the engine has never been affected.
The vocabulary, disentangled
OCIThe open standards for image format and runtime. The thing everything actually agrees on
containerdThe runtime Docker uses underneath, and which Kubernetes uses directly
runcThe low-level tool that actually creates the namespaces and cgroups
PodmanA daemonless, rootless-by-default alternative with a near-identical command line. Runs the same images
BuildKitThe modern build engine — parallel stages, better caching, build secrets. The default builder
On Kubernetes removing Docker. Kubernetes dropped dockershim in version 1.24, so Docker is no longer a container runtime for Kubernetes. This does not affect your images at all — they are OCI images and run unchanged on containerd. The headline caused considerable alarm and required no action from anyone building images.
What Docker is good at
  • Reproducible builds and environments — the same image everywhere, from a laptop to production
  • Local development — running dependencies without installing them on your machine
  • Packaging — a single artefact carrying the application and its runtime dependencies
  • CI — clean, isolated, disposable build environments
What it is not
  • Not an orchestrator. Compose is for a single host. Multi-host scheduling, self-healing and rolling updates are Kubernetes or an equivalent
  • Not a security boundary for untrusted code. Shared kernel — use a virtual machine or a sandboxed runtime
  • Not a substitute for configuration management of the host itself
  • Not automatically small or fast. A carelessly built image is enormous and slow to pull — see panels 5 and 6
The useful framing for production: Docker is your build and packaging tool; something else is your runtime. Most organisations build with Docker or BuildKit in CI, push to a registry, and run on Kubernetes or a managed container service. That division is worth being explicit about, because it decides which parts of this sheet you operate daily.
2  ·  IMAGES AND LAYERS — THE MODEL THAT EXPLAINS BUILD SPEED AND IMAGE SIZE JUNIOR what a layer is · STAFF why deleting a file does not shrink the image
An image is a stack of read-only layers plus metadata. Each layer records a set of filesystem changes. They are combined by a union filesystem into what looks like one coherent tree — and because layers are content-addressed and immutable, they are shared between images and cached between builds. Almost everything useful about Docker follows from this.
┌─────────────────────────────┐ │ writable container layer │ ← per container ├─────────────────────────────┤ │ COPY . /app │ ┐ │ RUN npm ci │ │ read-only │ COPY package.json . │ │ shared across │ FROM node:22-slim │ ┘ containers └─────────────────────────────┘
Consequences worth knowing
  • Every container starts as an image plus one thin writable layer. Ten containers from one image share the read-only layers entirely — which is why containers are cheap
  • Writes are copy-on-write. Modifying a file copies it up into the writable layer first, so write-heavy work on the container filesystem is slow. Use a volume
  • The writable layer dies with the container. Anything not in a volume is gone
  • Layers are shared on pull too — a layer already present is not downloaded again, which is why a common base image makes deployments much faster
The consequence that catches everyone: deleting a file in a later layer does not remove it from the image. A layer can only add a deletion marker — the original bytes remain in the earlier layer and are still in the image you push. So the image does not shrink, and anything sensitive written in an earlier layer stays retrievable by anyone who pulls it, however thoroughly a later step deletes it.
# WRONG — the credential is permanently in the image RUN wget --user=x --password=secret https://... RUN rm -rf /root/.netrc # does nothing useful # RIGHT — a BuildKit secret mount, never written to a layer RUN --mount=type=secret,id=npmrc \ npm ci --userconfig /run/secrets/npmrc
The build cache, and how it is invalidated
  • Each instruction produces a layer. Docker reuses a cached layer if the instruction and its inputs are unchanged
  • Once one layer misses, every layer after it rebuilds. This single rule dictates Dockerfile ordering
  • For COPY and ADD, the cache key includes file contents — so changing one source file invalidates everything downstream
  • For RUN, only the command string is compared — so apt-get update can serve a months-old cached layer. Combine it with the install in one instruction
Which gives the ordering rule: least-changing first. Base image, then system packages, then dependency manifests, then install, and your source code last. A code change then rebuilds one layer instead of reinstalling every dependency — routinely the difference between a five-second and a five-minute build.
3  ·  DOCKERFILE INSTRUCTIONS and the pairs people confuse
InstructionNotes
FROMThe base. Pin by digest for reproducibility; a tag can move underneath you
RUNExecutes at build time, creating a layer
COPYCopies files in. Prefer it to ADD
ADDAlso fetches URLs and auto-extracts archives — surprising behaviour, so use only when you want exactly that

CMD versus ENTRYPOINT
ENTRYPOINTWhat always runs. Arguments are appended to it
CMDDefault arguments, replaced entirely by anything given on the command line
The idiomatic pairing: ENTRYPOINT ["app"] with CMD ["--help"]. Running the image with no arguments prints help; running it with arguments passes them to the application.
The one that causes real production bugs: shell form does not forward signals. Written as CMD npm start, the shell becomes PID 1 and your application is a child — so SIGTERM reaches the shell, not your app. It never shuts down gracefully and is killed after the timeout on every single deploy. Use exec form — CMD ["npm", "start"] — so your process is PID 1 and receives the signal.

5  ·  BUILDING WELL — MULTI-STAGE, CACHE MOUNTS AND MULTI-ARCHITECTURE MID multi-stage builds · STAFF BuildKit features worth adopting
Multi-stage builds are the single most valuable technique here. Build in a stage containing compilers, source and development dependencies; copy only the finished artefact into a minimal final stage. The toolchain never reaches the shipped image, which cuts size dramatically and removes a large share of the vulnerability surface at the same time.
# ---- build stage ---- FROM golang:1.24 AS build WORKDIR /src COPY go.mod go.sum ./ # deps first — RUN go mod download # cached across code edits COPY . . RUN CGO_ENABLED=0 go build -o /app ./cmd/server # ---- final stage ---- FROM gcr.io/distroless/static:nonroot COPY --from=build /app /app USER nonroot:nonroot ENTRYPOINT ["/app"] # exec form — signals work # result: a few MB, no shell, no package manager, # non-root, and nothing from the build toolchain
Note the dependency ordering. Copying the manifest and downloading dependencies before copying source means a code change reuses the cached dependency layer. On a large project this is the difference between seconds and minutes on every build.
BuildKit features worth using
Cache mountsRUN --mount=type=cache,target=/root/.npm persists a package cache across builds without putting it in a layer. Large speed-up, no size cost
Secret mounts--mount=type=secret makes a credential available during one instruction and never writes it to a layer. The correct answer to private registries and build tokens
Bind mounts--mount=type=bind reads from the context without copying
Parallel stagesIndependent stages build concurrently, automatically
Cache exportPush and pull the build cache to a registry — this is how you get warm caches on ephemeral CI runners
Never pass secrets as build arguments. ARG values are recorded in the image history and are readable by anyone who pulls the image. The same applies to ENV. Use a secret mount — it is the only mechanism that keeps the value out of the image entirely.
Multi-architecture images
  • Increasingly necessary — developer machines on ARM, servers on x86, or both in a cloud fleet
  • docker buildx build --platform linux/amd64,linux/arm64 --push produces a manifest list, and clients pull the matching variant automatically
  • Native builders are far faster than emulation. Cross-building under QEMU works and is slow — use native runners per architecture where build time matters
A .dockerignore is not optional. The whole build context is sent to the daemon, so without one you ship .git, node_modules and local artefacts on every build — slowing it, and risking them landing in the image via a broad COPY ..
6  ·  BASE IMAGES & SIZE the trade you are actually making
BaseTrade-off
Full
debian, ubuntu		Everything present, easy to debug, large and a wide vulnerability surface
SlimThe same distribution with much removed. A good default — familiar tooling, far smaller
AlpineVery small. Uses musl rather than glibc, which occasionally causes subtle incompatibilities and performance differences in some runtimes. Verify rather than assume
DistrolessJust your application and its runtime — no shell, no package manager. Smallest attack surface, and you cannot exec into it to debug
ScratchGenuinely empty. Only for fully static binaries — no certificates, no timezone data unless you add them
The pragmatic default: slim for most languages, distroless for compiled binaries. Distroless gives an excellent security posture at essentially no cost when your artefact is a single static binary, and it is more disruptive for interpreted languages where you may need a shell.
Alpine is not automatically the right choice. It is genuinely smaller, and the musl difference has produced real, hard-to-diagnose issues — including DNS resolution behaviour and performance regressions in certain language runtimes. If you use it, test properly under load rather than assuming equivalence with a glibc image.
Why size actually matters
  • Pull time on every new node — significant when autoscaling, and directly visible as slow scale-up
  • Storage across registry, nodes and caches, multiplied by every tag retained
  • Attack surface — every package present is something to patch and something an attacker can use
  • Scan noise — a full base image generates hundreds of findings in components you never invoke
Debugging a distroless image is done by attaching a separate debug container that shares the process namespace, rather than by adding a shell to production. That is the correct shape — the production image stays minimal and the tools arrive only when needed.
7  ·  NETWORKING — DRIVERS, DNS AND THE MISTAKES EVERYONE MAKES ONCE JUNIOR port publishing · MID why the default bridge is the wrong one
DriverBehaviour
bridge
the default		A private network on the host, with NAT out. Containers get internal addresses and reach the outside; inbound needs published ports
User-defined bridgeWhat you should actually use. Same idea, plus automatic DNS resolution by container name — and better isolation between groups of containers
hostNo network namespace — the container shares the host stack directly. Fastest, no isolation, port conflicts are real. Linux only
noneNo networking at all. Useful for genuinely isolated batch work
macvlanThe container gets an address on the physical network, appearing as its own host. For legacy integrations
overlayMulti-host networking for Swarm. On Kubernetes this is the CNI's job instead
Always create a user-defined network for related containers. On the default bridge, containers cannot resolve each other by name — the old --link flag existed for this and is deprecated. On a user-defined network, http://api:8080 simply works, which is also exactly what Compose sets up for you.
Port publishing
docker run -p 8080:80 nginx │ └── container port └─────── host port -p 127.0.0.1:8080:80 # bind to loopback only -p 80 # random host port
Publishing binds to all interfaces by default. On a server with a public address, -p 5432:5432 exposes your database to the internet — and it typically bypasses the host firewall, because Docker writes its own iptables rules. Bind explicitly to 127.0.0.1 for anything that should not be publicly reachable.
Three mistakes everyone makes once
  • localhost inside a container is the container. Your application cannot reach a database on the host that way. Use the service name on a shared network, or host.docker.internal on Docker Desktop
  • An application bound to 127.0.0.1 inside the container is unreachable however you publish it. Bind to 0.0.0.0 — this is one of the most common “the port is published but nothing responds” causes
  • EXPOSE publishes nothing. It is metadata. Only -p at run time opens a host port
On Docker Desktop, containers run inside a virtual machine, so networking and bind-mount performance behave differently from Linux. Behaviour that works on a developer laptop and fails on a Linux server usually traces back to this.
8  ·  VOLUMES & STORAGE where data actually survives
The container filesystem is ephemeral. Everything written outside a mount lives in the writable layer and is destroyed when the container is removed. Anything that must survive belongs in a volume, a bind mount, or an external service.
TypeUse
Named volumeManaged by Docker in its own storage area. The right choice for production data — portable, backed up as a unit, and it avoids host path and permission problems
Bind mountA host path mounted in. Ideal for development — live code reload — and fragile in production, since it depends on host layout and permissions
tmpfsIn memory, never on disk. For secrets or scratch data that must not be written down
Things worth knowing
  • Volumes are not removed with the container unless you ask. Anonymous volumes accumulate silently — docker volume prune and docker run --rm -v help
  • Bind-mount permissions are a common trap. The container's user id must match the host file ownership, or writes fail with confusing errors. Named volumes avoid this
  • Bind mounts on Docker Desktop are slow, because they cross a virtual machine boundary. Large dependency directories are noticeably affected
  • A mount hides whatever was underneath at that path in the image
  • :ro mounts read-only — use it for configuration you do not want a container to modify
Back up the volume, not the container. Containers are disposable by design; the volume holds everything of value. And test the restore — a volume backup nobody has restored is an assumption.
Run with a read-only root filesystem where you can — --read-only plus a tmpfs for genuinely temporary paths. It prevents a compromised process from modifying the application, and it surfaces unexpected writes during testing rather than in production.
9  ·  DOCKER COMPOSE single-host, and V1 is gone
Two corrections that still appear in current material. Compose V1 reached end of life and is no longer shipped or supported — the Python docker-compose binary has been removed from official images and CI runners. Use docker compose, with a space: it is a CLI plugin. And the version: key at the top of the file is obsolete — it is ignored and produces a warning.
# no version: key needed services: api: build: . ports: ["8080:8080"] environment: DB_HOST: db # resolves by service name depends_on: db: condition: service_healthy db: image: postgres:17 volumes: [pgdata:/var/lib/postgresql/data] healthcheck: test: ["CMD-SHELL", "pg_isready -U postgres"] interval: 5s retries: 10 volumes: pgdata:
The classic Compose bug: plain depends_on waits for the container to start, not for the service to be ready. Your application starts before the database accepts connections and crashes. Use condition: service_healthy with a healthcheck, as above — and make the application retry its connection regardless, because it will meet this in production too.
Useful features
  • Automatic networking — every service is resolvable by name on a shared user-defined network
  • Profiles — mark optional services so --profile starts them only when wanted
  • Override files — a base file plus docker-compose.override.yml for local differences
  • watch — sync files or rebuild automatically on change, for a fast development loop
Compose is not a production orchestrator. One host, no rescheduling, no rolling updates, no self-healing beyond restart policies. It is excellent for development, CI and genuinely simple single-host deployments — and reaching for it as a Kubernetes substitute at scale ends badly.
10  ·  RUNTIME & RESOURCES limits, restarts and PID 1
Resource limits
docker run \ --memory=512m \ # hard limit — OOM kill above --memory-reservation=256m \ --cpus=1.5 \ # 1.5 cores' worth --pids-limit=200 \ # fork-bomb protection --restart=unless-stopped \ myapp:1.4.2
Without limits a container can consume the whole host. Memory especially — one leaking container can trigger the host out-of-memory killer, which may then kill something else entirely. Set memory limits on anything sharing a host.
Many runtimes do not see the cgroup limit by default and size their heap or thread pools from the host's CPU and memory. The result is a process that immediately allocates more than its limit and is killed. Modern JVMs and Node versions handle this correctly — older ones need explicit flags, and it is worth verifying rather than assuming.
Restart policies
noThe default. No automatic restart
on-failure[:n]Restart on a non-zero exit, optionally capped
alwaysAlways restart, including after daemon restart
unless-stoppedLike always, but respects a manual stop. Usually what you want
PID 1 and zombie processes
  • PID 1 has special duties — it must reap orphaned child processes. Most applications do not, so if yours spawns children, zombies accumulate
  • --init inserts a minimal init process that reaps correctly and forwards signals. Cheap insurance for anything that forks
  • Exec form still matters — with shell form your process is not PID 1 and never receives SIGTERM
Configure log rotation. The default JSON file driver grows without limit, and a chatty container will fill the host disk. Set max-size and max-file, or ship logs elsewhere.
11  ·  SECURITY defaults are convenient, not safe
The default is root. Unless the image sets a USER, your process runs as root inside the container — and with a shared kernel, that is a materially worse position than running as an ordinary user. This one line is the highest-value change in the panel.
In the image
  • Create and switch to a non-root user, and make sure the application does not need to write where it cannot
  • Pin the base image by digest, not by a mutable tag
  • Multi-stage builds so compilers and build credentials never ship
  • No secrets in ARG, ENV or any layer — use build secrets, and inject runtime secrets from the platform
  • Rebuild regularly to pick up base-image patches. An image built a year ago carries a year of unpatched vulnerabilities
At run time
  • Never --privileged unless you genuinely need full host access — it disables essentially every protection
  • Drop all capabilities and add back only what is needed — --cap-drop=ALL
  • --security-opt=no-new-privileges to block privilege escalation
  • Read-only root filesystem plus tmpfs for writable paths
  • Keep seccomp and AppArmor profiles enabled — the defaults are useful and disabling them is common and unwise
Do not mount the Docker socket into a container. It is the single most common serious misconfiguration — CI runners, dashboards and agents all ask for it. A container with the socket has root on the host. Where a build genuinely needs to build images, use a rootless builder or a dedicated build service rather than handing over the daemon.
12  ·  REGISTRIES AND THE SUPPLY CHAIN MID tags versus digests · STAFF signing, provenance and what to actually enforce
Tags are mutable pointers; digests are immutable content. myapp:1.4.2 can be repushed to mean something entirely different tomorrow. myapp@sha256:abc… is that exact image, permanently. “It worked yesterday and the tag has not changed” is not evidence of anything unless you pinned the digest.
Tagging that works
  • Immutable, meaningful tags — a version and the commit SHA. Never reuse one
  • Enable tag immutability in the registry if it supports it, so a push cannot overwrite an existing tag
  • :latest is a convention, not a feature — it is simply the default tag, points wherever it was last pushed, and should not appear in any deployment
  • Deploy by digest for anything you must be able to reproduce
  • Build once and promote the same digest through environments. Rebuilding per environment means you tested a different artefact from the one you shipped
Docker Hub applies pull rate limits to anonymous and free accounts, which surfaces as sporadic CI failures under load. Authenticate, or mirror through a pull-through cache — this catches teams out at exactly the wrong moment.
Supply-chain controls worth having
ScanningIn CI and again in the registry, since new vulnerabilities are found in images that have not changed. Scanning only at build time means you stop learning about an image the moment you ship it
SBOMA generated inventory of what is inside. The thing that answers “are we affected?” in hours rather than weeks when the next widespread vulnerability lands
SigningSign images and verify signatures at deploy time. A signature nobody checks provides no protection
ProvenanceAttestations recording how and where an image was built — which source, which builder, which inputs
Base image policyAn approved, maintained set of bases. Fixing a vulnerability in one place beats fixing it in two hundred Dockerfiles
The highest-return practices, in order: pin base images by digest, rebuild on a schedule so patches actually reach production, scan continuously rather than once, and enforce at admission so an unsigned or unscanned image cannot run. The first two cost almost nothing and close most of the real gap.
The failure this prevents is mundane and common: an image built eighteen months ago, still running, carrying every base-image vulnerability disclosed since. Nothing changed, which is exactly the problem — and no scan at build time would have told you.
13  ·  DEBUGGING the commands that matter
# why did it stop? docker ps -a # exit code and status docker logs --tail 100 -f <id> docker inspect <id> # full config and state # what is it doing now? docker exec -it <id> sh # if there is a shell docker stats # live CPU and memory docker top <id> # processes # why is the image so big? docker history --no-trunc <image> docker image inspect <image> # what changed in the writable layer? docker diff <id> # reclaim space docker system df # what is using it docker system prune -a --volumes # careful
Exit codes worth recognising
0Clean exit — for a service, that usually means it finished when it should not have
1Application error. Read the logs
125The daemon rejected the run command — a bad flag, not your app
126The command was found but is not executable — often a missing execute bit or wrong architecture
127Command not found — usually a typo or a binary missing from a slim base
137SIGKILL — nearly always an out-of-memory kill. Check the memory limit
143SIGTERM — a normal stop
Exit 137 is the one to memorise. It means the kernel killed the process for exceeding its memory limit — not an application bug, and no amount of reading logs will show it, because the process was killed without warning.
To debug a distroless or scratch image, attach a second container sharing its process and network namespaces: docker run --rm -it --pid=container:<id> --network=container:<id> nicolaka/netshoot. You get a full toolkit without adding anything to the production image.
14  ·  PRODUCTION PRACTICE — CI/CD, HOST OPERATIONS AND WHERE DOCKER FITS how images should flow to production, what the host needs, and the boundary with orchestration
The pipeline that works
  1. Build once, from a commit, producing one digest
  2. Tag with the version and commit SHA, never reusing a tag
  3. Scan, generate an SBOM, sign and attach provenance
  4. Push to a registry with immutability enabled
  5. Promote the same digest through staging to production — never rebuild per environment
  6. Verify the signature at deploy, and reject anything unsigned
Rebuilding per environment is the anti-pattern to name. A rebuild picks up different base-image content, different transitive dependencies and a different build clock — so the artefact you tested is not the one you shipped. One build, many deployments.
Making CI builds fast
  • Export the build cache to a registry — ephemeral runners start cold otherwise, and this is the single biggest CI build improvement available
  • Order the Dockerfile for cache reuse; a proper .dockerignore keeps the context small
  • Use cache mounts for package managers
  • Build architectures on native runners rather than under emulation
  • Do not mount the Docker socket into CI jobs — use a rootless or remote builder
Running containers on a host directly
  • Resource limits on everything — memory especially, so one container cannot take the host down
  • Restart policy set, usually unless-stopped
  • Log rotation configured, or the disk fills
  • Prune on a schedule. Unused images, stopped containers, dangling volumes and the build cache accumulate steadily — disk exhaustion from unpruned Docker data is a genuinely common outage
  • Healthchecks defined, so the runtime knows the difference between running and working
  • Watch the storage driver's disk usage separately from application data
  • Keep the daemon and the host kernel patched — the kernel is shared, so a host vulnerability is a container vulnerability
docker system prune -a is destructive. It removes images not currently used by a running container — including ones you were relying on being cached, and images for containers that happen to be stopped. On a production host, prune deliberately rather than broadly.
Where Docker stops and orchestration begins
NeedAnswer
Build and packageDocker or BuildKit. Still the standard, whatever runs the result
Local developmentCompose. Excellent at this and worth keeping
One host, a few servicesCompose with restart policies, or a systemd unit per container. Genuinely fine
Multi-host, rolling updates, self-healingKubernetes, or a managed container service
Scale to zero, request-drivenA serverless container platform
The boundary worth being clear about: Docker builds the artefact; the orchestrator decides where it runs, how many, what happens when one dies, and how traffic reaches it. Those are different problems, and Compose deliberately does not solve the second set.
A note on skipping the middle. Many teams move from a single host straight to Kubernetes and inherit a large operational burden they did not need. A few containers on one well-configured host, with limits, healthchecks and log rotation, is a legitimate production architecture — and it is much easier to operate well.

What breaks first
#Limit
1Build cache ordering. Slow builds on every commit — the most frequent complaint, and a five-minute fix
2Ephemeral data assumptions — writing where nothing survives
3Signal handling, so nothing shuts down cleanly and deploys drop requests
4Host disk exhaustion from unpruned images, cache and logs
5Container runtime performance — very rarely the actual problem
Note the order. None of the top four are about container performance. They are Dockerfile ordering, storage choices, one line of process handling and routine housekeeping.
Triage order
  1. docker ps -a — is it running, and what was the exit code?
  2. docker logs — what did it say before stopping?
  3. docker inspect — is the configuration what you believe it is?
  4. docker stats — is it near a resource limit?
  5. docker exec, or an attached debug container for a minimal image
Steps 1 and 2 resolve the large majority. The exit code alone usually names the category — 137 is memory, 127 is a missing command, 125 is a bad run command rather than your application.
