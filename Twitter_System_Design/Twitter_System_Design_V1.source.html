Availability arithmetic, stated properly. Serial dependencies multiply: a read path touching five services at 99.9% each yields roughly 99.5% composite — about 44 hours a year. Quoting 99.99% for a long synchronous chain is arithmetic, not ambition, which is why so much of this design pushes work off the read path.
The defining characteristic
This is a read-dominated system with an extreme fan-out asymmetry. Reads outnumber writes by roughly two orders of magnitude — and one write can require millions of downstream writes, or none, depending entirely on who posted it. Nearly every decision on this sheet exists to manage that asymmetry.
Why the home timeline is the hard part
A home timeline is a merged, ranked view of tweets from everyone you follow. Computing it naively at read time means querying hundreds of users' recent tweets, merging and ranking them — per request, at hundreds of thousands of requests per second. That is not achievable, so the timeline is precomputed. Precomputing it is what creates the celebrity problem.
The follower distribution is the whole story
UserFollowersFan-out cost per tweet
Median user~ hundredsTrivial
Popular account~ 100 KNoticeable
Celebrity10 M – 100 M+Catastrophic if handled the same way
This is a power-law distribution, not a normal one. Designing for the average user produces a system that collapses on the tail — and the tail is precisely the traffic that matters most commercially.

3  ·  CAP AND PACELC — PER CAPABILITY, NOT PER SYSTEM the framing that is usually stated wrongly, and what each part of this platform actually chooses
The correction: CAP is not “pick two of three”. You do not choose partition tolerance — partitions happen whether you want them or not, so any distributed system must tolerate them. The real statement is narrower: during a partition, choose consistency or availability. With no partition you get both. A diagram that says “pick two” and then adds “we always need P” is contradicting itself.
PACELC is the version you actually use. If Partition → choose A or C; Else → choose Latency or Consistency. Partitions are rare; the latency-versus- consistency trade-off is made on every single request, which makes it the more useful lens.
And it is chosen per capability. This platform is CP for authentication and AP for timelines — often within one request. “Our system is AP” is the answer of someone who has read about CAP rather than applied it.
The trade this product deliberately makes
A tweet appearing in a follower's timeline seconds late is invisible to users. A timeline that fails to load is not. That asymmetry is why nearly everything on the read path chooses availability — and it is a product judgement expressed as an architectural one.

5  ·  THE FAN-OUT PROBLEM — THE HEART OF THIS DESIGN what the question is actually testing · MID the two strategies · STAFF where the boundary goes and why
The two pure strategies
Fan-out on write  pushFan-out on read  pull
On postAppend the tweet id to every follower's stored timelineDo nothing
On readReturn the stored list — one lookupQuery every followee's recent tweets, merge and sort
Read latencyExcellent — a list readPoor — hundreds of queries per request
Write costO(followers) — unboundedO(1)
StorageOne entry per follower per tweetNone
Breaks whenSomeone has millions of followersEveryone reads constantly — which they do
Neither works alone, and saying so is the answer. Pure push cannot survive a celebrity: one tweet becomes tens of millions of writes, and if they post ten times a day the fan-out system does nothing else. Pure pull cannot survive the read volume: at ~175,000 reads per second, each fanning out to hundreds of queries, the numbers are absurd.
The hybrid — what is actually built
// on post followers = graph.count(author) if followers < THRESHOLD: // ~10k, tuned push → append id to each follower's list else: skip → store nothing; readers will pull // on read timeline = redis.lrange(user, 0, n) // pushed celebs = pullRecent(followedLargeAccounts) // pulled return rank(merge(timeline, celebs))
Why the split works. Ordinary users have few followers, so pushing is cheap. Celebrities have many followers but post rarely relative to their reach, so pulling is bounded — and the pull is shared: one fetch of a celebrity's recent tweets serves every follower reading at that moment.
STAFF Choosing the threshold
  • It is a tuning parameter, not a constant. Order of ten thousand followers is a common landing point, arrived at by measuring — not derived from first principles
  • Too low → too many accounts pulled, so every read does more work and read latency degrades
  • Too high → fan-out queues back up during peak posting, and timelines fall behind
  • Consider posting rate as well as follower count. A million-follower account that posts once a month is cheap to push; a fifty-thousand-follower account posting constantly may be worth pulling
  • It must be changeable at runtime — a configuration value with a kill switch, not a deploy
The refinement worth mentioning. Fan out only to active followers. A large share of accounts have not opened the app in months, and materialising timelines for them is pure waste. Push to recently-active users, and rebuild on demand for anyone returning — this can remove the majority of fan-out work.
What the fan-out worker must handle
  • Idempotency — Kafka redelivers, and a replayed event must not duplicate the entry
  • Capping — LPUSH then LTRIM to a fixed length; timelines are bounded, not infinite
  • Batching — write in chunks rather than one call per follower
  • Backpressure — lag is the metric that matters; alert on it, not on error rate
  • Prioritisation — active followers first, so the people who will actually read it get it soonest
STAFF The question that separates depth: what happens when fan-out lags? Timelines fall behind silently — no error, no alert unless you built one. Users see stale feeds and nothing in the system considers itself unhealthy. Monitor consumer lag as a primary SLI, shed the lowest value work first, and be able to fall back to pull for accounts whose push is behind.
6  ·  TWEET IDs — SNOWFLAKE a detail worth knowing
Every tweet needs a unique id, generated at thousands per second across many machines, with no coordination — and ideally sortable by time, so that ordering a timeline is ordering integers.
Why the obvious options fail
Auto-incrementRequires a single writer. A coordination point in the hottest path
Random UUIDUnique and coordination-free, but not sortable — so ordering needs a separate timestamp and index, and insert locality is poor
Timestamp aloneCollides — many tweets share a millisecond
The Snowflake layout
64 bits, most significant first 1 bit unused keeps the value positive 41 bits timestamp ms since a custom epoch ≈ 69 years of range 10 bits machine up to 1,024 workers 12 bits sequence 4,096 ids per ms per machine // capacity: 1,024 × 4,096 = ~4.2 M ids per ms // far beyond any plausible tweet rate
The property that makes it valuable. Because the timestamp occupies the high bits, sorting ids sorts by time. Timeline merges, pagination cursors and range scans all become integer comparisons — no separate timestamp column, no secondary index, no clock comparison across machines.
The failure mode to name: clock skew. If a machine's clock moves backwards — an NTP correction, a leap second — it can generate an id it has already issued. The generator must detect a backwards clock and refuse to issue ids until time catches up, rather than producing a duplicate. Refusing briefly is recoverable; a duplicate tweet id is not.
The general lesson beyond this system. Sortable, coordination-free identifiers are useful anywhere you need ordering without a central sequence — which is why ULID and UUIDv7 exist and follow the same time-high-bits idea.
7  ·  TIMELINE STORAGE, RANKING AND THE OPERATIONS THAT ARE HARD AFTERWARDS MID the cache structure · STAFF ranking, deletion, editing and ordering guarantees
The stored timeline
// one capped list of ids per user key: timeline:{user_id} type: list of tweet ids (8 bytes each) size: ~800 entries, hard capped LPUSH timeline:{u} {tweet_id} LTRIM timeline:{u} 0 799 // bounded // 250M users × 800 × 8B ≈ 1.6 TB — fits in memory // storing tweet OBJECTS instead would be ~100× more
Bounding the list is what makes this affordable. Nobody scrolls back a thousand entries in a home timeline; anyone who does can be served from the user timelines directly. Unbounded per-user storage would grow without limit for no product benefit.
Ranking — the timeline is not chronological
  • Candidate generation — the merged push and pull sets, typically hundreds of tweets
  • Scoring — engagement signals, author affinity, recency decay, media type, predicted interaction
  • Policy — deduplicate, cap consecutive tweets from one author, inject what must be shown, remove what must not
  • Cost note — scoring is bounded because the candidate set is small. The precomputation is what makes ranking affordable at read time
Offer chronological as an option. Some users strongly prefer it, and it is nearly free — it is the merged list before scoring. Being able to say why it costs almost nothing shows you understand where the expense actually sits.
STAFF The operations that are awkward after fan-out
OperationWhy it is hard, and how it is handled
Delete a tweetThe id sits in millions of stored timelines. Do not remove it from each one. Delete the object and filter at hydration — a missing or tombstoned object simply does not render. Timelines self-clean as they roll over
Edit a tweetFree, because timelines hold ids. Update the object once and every timeline shows the new version. Keep an edit history for auditability
Block or muteApplied at read, from a small cached set. Rewriting stored timelines on every block would be unbounded work for a trivial action
Account suspensionSame mechanism as delete, at the author level — filter at hydration rather than purge
New followThe new followee's past tweets are absent from the stored timeline. Backfill a bounded window, or let it fill naturally and pull recent ones
UnfollowTheir ids remain until they age out. Filtered at read; not worth rewriting
The principle running through every row: never rewrite fanned-out data. Anything that would require touching millions of stored timelines to satisfy one user action must instead be handled by filtering at read time. This is the single most useful heuristic in this design, and it generalises well beyond it.
STAFF The ordering guarantee, stated honestly. There is no global ordering across the timeline. Push and pull arrive on different paths with different latencies, so two users may briefly see the same tweets in a different order. Snowflake ids give a consistent sort once everything has arrived — the guarantee is eventual convergence, not real-time global order, and claiming otherwise would be false.
8  ·  THE SOCIAL GRAPH a correction worth making
A graph database is usually the wrong answer here, and it is a common reflex. Graph engines earn their cost on variable-depth traversal — friends-of-friends-of-friends, shortest path, community detection. The follower graph's hot operations are far simpler than that.
What the access patterns actually are
Who follows X?Read one adjacency list — for fan-out
Who does X follow?Read one adjacency list — for pull and backfill
Does X follow Y?A single membership check
How many followers?An approximate counter
Every one of those is a key lookup or a membership test — which a sharded key-value or wide-column store serves faster, cheaper and more predictably than a graph engine. Store both directions explicitly: followers-of and following-of as separate lists, written together, because both are read hot.
Practical concerns
  • Shard by user id, so one user's list is on one node
  • Very large lists need paging — a hundred-million-follower list is never returned whole; cursor over it
  • Counts are approximate and maintained separately. An exact follower count at this scale is a distributed-counter problem with no product benefit
  • Writes are small but must be strongly consistent — an unfollow or block that does not take effect is a safety issue, not a stale read
  • Hot shards — celebrity accounts concentrate load on one partition; cache their lists aggressively
When a graph store would be right: a “people you may know” feature doing multi-hop traversal, or fraud-ring detection over the follow graph. Those are genuine graph problems — and they belong in an offline system, not on the serving path.
9  ·  SEARCH real-time, over an append-only corpus
Search here has an unusual shape: the corpus is enormous, append-only and dominated by recency. Almost all queries want recent tweets; very few want something from years ago. That skew is what the design exploits.
The indexing pipeline
tweet → outbox → Kafka → indexer → inverted index └▶ vector index (semantic) // never dual-write to the store and the index — // that leaves the index silently wrong, with no error
Partitioning by time
  • Recent shards are small, hot and in memory; older shards are large, cold and rarely touched
  • Most queries hit only the recent shards, so the effective search space is a fraction of the corpus
  • Old shards can be moved to cheaper storage or dropped entirely, according to a retention policy
This is the highest-leverage decision in the panel. Time-partitioning turns “search billions of documents” into “search the last few hours, and only widen if the query demands it”.
Query concerns
  • Relevance scoring — BM25 as a baseline, plus engagement and author signals
  • Recency versus relevance is a product decision, exposed as top-versus-latest
  • Filters — author, language, media, date range, safety
  • Hybrid retrieval — keyword for exact handles and hashtags, vector for meaning. Fuse the ranked lists
The index is a projection, never the source of truth. It must be fully rebuildable from the tweet store, and rebuilding should be a rehearsed operation — you will need it after a mapping change, and discovering that during an incident is the wrong time.
10  ·  TRENDING TOPICS approximate on purpose
Trends answer “what is being discussed unusually much, right now”. Exact counting across billions of terms is neither achievable nor necessary — nobody can tell whether a hashtag was mentioned 48,000 or 49,000 times.
Why exact counting is the wrong goal
  • Every tweet contains many candidate terms, so the counting rate is a large multiple of the tweet rate
  • The term space is effectively unbounded and constantly changing
  • Only the heavy hitters matter — the top tens per region, not the full distribution
The approach
Sliding windowsCount over recent intervals — five minutes, an hour — not all time
Probabilistic countingCount-Min Sketch for approximate frequency in fixed memory; heavy-hitter algorithms to surface the top terms
Rate of changeThe signal is acceleration, not volume. Common words are always frequent; a trend is a term unusually frequent compared to its own baseline
Geo and language partitioningTrends are computed per region, which also bounds the term space per shard
Safety filteringApplied before publication, not after
The insight to state. Comparing against a baseline is what distinguishes a trend from a popular word. Ranking by raw count surfaces the same generic terms every hour and is useless as a product — which is why the metric is deviation from expectation rather than volume.
Serving is trivial once computed. The output is a small ranked list per region, refreshed every few minutes and cached at the edge. All the engineering is in the aggregation, none in the read.
11  ·  MEDIA & NOTIFICATIONS bytes and second-order fan-out
Media — never on the tweet path
  1. Client requests a pre-signed upload URL and uploads directly to object storage — the bytes never pass through your services
  2. The upload emits an event; a pipeline transcodes and generates size and format variants
  3. The tweet references a media id; the CDN serves the variants
  4. The tweet can be posted while processing continues, with a placeholder until ready
Direct-to-storage upload is the decision that matters. Routing media through application servers wastes bandwidth, memory and connection capacity on the busiest tier for no benefit — and it makes a large upload capable of degrading unrelated requests.
Media dominates cost, not tweets. Text is bytes; video is orders of magnitude more, and egress is usually the largest line on the bill. CDN offload ratio is the single highest-leverage cost metric in the whole system.
Notifications — the second fan-out
  • Likes and retweets on a popular tweet are their own fan-out problem, in the opposite direction — millions of events converging on one author
  • Aggregate rather than deliver individually — “and 12,000 others” is both better product and vastly cheaper
  • Coalesce over a window so one person's burst of activity is one notification
  • Mentions of a large account need rate limiting, or a pile-on becomes a denial of service on the notification path
  • Push delivery is best-effort; the in-app list is the durable record
A good interview observation: notifications have the inverse shape of timelines — many writers, one reader. It is the same fan-out mathematics reflected, and aggregation is the equivalent of the hybrid strategy.

Post a tweet
POST /v1/tweets Authorization: Bearer … Idempotency-Key: 01J8F3K2M9Q { "text": "Hello world", "media_ids": ["m_1029"], "in_reply_to": null } HTTP/1.1 201 Created { "id": "1729384756102938624", // Snowflake "author_id": "u_8813", "text": "Hello world", "created_at": "2026-09-01T10:14:22Z", "metrics": { "likes": 0, "retweets": 0, "replies": 0 } }
The idempotency key is not optional here. A user on a poor connection taps post, the response is lost, the client retries — and without a key they have tweeted twice publicly. It is the most visible possible failure, and it is entirely preventable.
The id is returned as a string. A 64-bit Snowflake id exceeds what JavaScript represents exactly as a number, so serialising it as an integer silently corrupts the low digits in browser clients. This is a real and well-known class of bug.
Read the home timeline
GET /v1/timelines/home?limit=50&cursor=17293847… HTTP/1.1 200 OK RateLimit-Limit: 900 RateLimit-Remaining: 887 { "data": [ { "id": "172938…", "text": "…", "author": { "id": "u_44", "handle": "…" }, "metrics": { … } }, … ], "meta": { "next_cursor": "1729384750000000000", "result_count": 50 } }
Cursor pagination, never offset. The timeline changes constantly, so offset=100 returns a shifting window — users see duplicates and miss tweets. A cursor is a position in an ordered sequence, and because Snowflake ids sort by time, the id itself is the cursor.
Conventions applied throughout
  • Versioned in the path; breaking changes get a new version
  • One error envelope with a stable machine-readable code
  • Rate limit headers on every response, not only on 429 — clients can then slow down before being limited
  • Read and write limits differ by an order of magnitude, matching the traffic each protects

The principle. Reads degrade gracefully; writes fail loudly. A stale or unranked timeline is acceptable; silently losing a user's post is not.
What breaks first
#Limit
1Fan-out consumer throughput during a posting peak — it lags before anything errors
2Cache memory and hot keys, particularly around a trending event
3Kafka partition skew — a hot author concentrates load on one partition
4Database connection pools, which saturate long before CPU does
5Media egress and cost, which is a budget limit rather than a technical one
Note that the first three are all fan-out or cache. The tweet database — the thing most designs spend their time on — is nowhere near the top of this list.
What to monitor above all
  • Fan-out consumer lag, and the age of the oldest unprocessed event
  • Timeline cache hit rate — a fall here precedes every read incident
  • Timeline read p99, split by push-heavy and pull-heavy users
  • Post success rate — the one metric that means the product works
  • Tweets fanned out per second versus tweets posted per second — the amplification factor, live
