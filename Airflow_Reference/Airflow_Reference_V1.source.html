1  ·  WHAT AIRFLOW IS, WHAT IT IS NOT, AND WHAT AIRFLOW 3 CHANGED start here — the single most valuable principle is that Airflow orchestrates work rather than performing it
The definition
A platform to author, schedule and monitor workflows as code. Workflows are Python files defining a directed acyclic graph of tasks with dependencies between them. Airflow decides what runs when, in what order, and what to do when something fails.
The principle that prevents most Airflow problems: orchestrate, do not compute. Airflow should tell other systems to do work — trigger a Spark job, run a warehouse query, call an API — and track the outcome. It should not load a dataframe, join it and write it back. Tasks that process data themselves make workers the bottleneck, make memory a scheduling concern, and make the platform impossible to scale independently of the work.
What it is not, stated plainly
Not a data processing engineUse Spark, dbt or the warehouse. Airflow launches them
Not a streaming platformIt is batch-oriented. Sub-minute or event-per-record work belongs in Kafka, Flink or a queue consumer
Not a low-latency schedulerScheduling latency is measured in seconds. It is not a cron replacement for second-level precision
Not an ETL toolIt is the conductor. The instruments are elsewhere
Where it genuinely excels: batch pipelines with real dependency graphs, heterogeneous systems that must be coordinated, work needing retries and backfills, and anywhere the schedule and dependency logic itself is complex enough to deserve version control.
STAFF Airflow 3 arrived in 2025 and it is a genuine break, not a point release. A reference written for 2.x will teach several things that no longer work. The headline changes are worth knowing whichever version you run, because they signal the direction.
What Airflow 3 added
  • Task SDK and a Task Execution API — tasks run with full isolation from the metadata database, which removes a long-standing security and coupling problem. Authors now import from the airflow.sdk namespace
  • DAG versioning — structural changes are tracked over time, so you can inspect the DAG as it was when a historical run executed. This closes a real gap in debugging
  • Assets — the dataset model renamed and redesigned, with an @asset decorator and a cleaner event-driven model. Airflow can now watch external assets and trigger on change
  • Edge Executor for distributed and edge workloads, now generally available
  • A rebuilt UI on React and FastAPI, with version-aware views and backfill management
  • Scheduler-managed backfills, rather than a separate CLI-driven mechanism
What Airflow 3 removed — check your DAGs against this list. SubDAGs and SubDagOperator are gone entirely; use TaskGroups. SequentialExecutor is gone; LocalExecutor now handles SQLite and is the local-testing answer. SLAs are removed. DAG and XCom pickling are removed. execution_date is removed. And schedule_interval, deprecated since 2.4, is removed in favour of schedule.

A note on the ecosystem. Airflow's real strength is the provider packages — hundreds of them, covering every major cloud, database, warehouse and SaaS platform. Before writing a custom operator, check whether a provider already does it; a maintained provider handles authentication, pagination, retries and deferrability that a hand-written hook will not.
2  ·  CORE CONCEPTS AND THE DATA INTERVAL — THE PART EVERYONE GETS WRONG JUNIOR the vocabulary · STAFF why your daily DAG runs a day “late”, and why that is correct
ConceptWhat it is
DAGA Python file describing tasks and their dependencies. A definition, not a run
TaskA node in the graph — one unit of work
OperatorA template for a task. BashOperator, PythonOperator, and hundreds from providers
Task instanceOne specific execution of a task, for one DAG run. This is what actually has a state
DAG runOne execution of the whole DAG, for one logical date
HookThe connection layer to an external system. Operators use hooks
SensorA task that waits for a condition. See panel 11 — these cause more trouble than any other task type
XComSmall messages passed between tasks, stored in the metadata database
PoolA named concurrency limit shared across tasks
AssetA logical dataset a DAG produces or consumes, enabling data-aware scheduling instead of time-based
The state model to know: a task is scheduled → queued → running → success or failed, with up_for_retry, up_for_reschedule, skipped and upstream_failed along the way. Tasks stuck in queued mean the executor cannot place them — a capacity or pool problem, not a code one.
The data interval is the single most confusing concept in Airflow, and it is worth being precise about. A scheduled DAG run does not represent “now”. It represents a period of data — and it runs after that period has ended, because only then is the data complete.
# a DAG with schedule="@daily" data_interval_start 2026-03-01 00:00 data_interval_end 2026-03-02 00:00 ↓ the run is triggered at 2026-03-02 00:00 # because only then is 1 March complete # so on the morning of 2 March, the most recent # successful run is labelled 1 March. # This is correct. It is not a delay.
Use the interval, not the clock. A task that queries WHERE date = today() is not idempotent and will produce different results on a rerun or a backfill. Use data_interval_start and data_interval_end from the context, and the same task run at any time produces the same result — which is what makes backfills meaningful.
A version note that matters when reading older material. In Airflow 2, logical_date equalled data_interval_start. In Airflow 3 it equals the run-after time instead. The data interval fields are unchanged and are what you should reference in task logic either way.
And the footgun: catchup defaults to true. Deploy a DAG with a start_date two years ago and Airflow will attempt to run every missed interval — hundreds of runs launching at once, saturating workers and possibly hammering a source system. Set catchup=False unless you specifically want history, and pair it with max_active_runs.
3  ·  SCHEDULING time-based and data-aware
FormExample
Cron"0 6 * * *" — daily at 06:00. Standard five-field syntax
Presets@daily, @hourly, @weekly, @monthly, @once
Timedeltatimedelta(hours=6) — relative to the previous run rather than to a wall clock
NoneTriggered manually or by another DAG only
TimetableA custom Python class. The answer for business days, trading calendars or irregular schedules that cron cannot express
AssetsRun when an upstream DAG produces a dataset — data-aware rather than time-based
Asset-based scheduling is the most under-used feature here. Instead of guessing that upstream finishes by 06:00 and scheduling for 06:30, declare that your DAG consumes an asset the upstream DAG produces. It then runs when the data is actually ready — no padding, no silent breakage when upstream slows down. Airflow 3 extends this to watching external assets and triggering on external events.
Catchup and backfill
  • catchup=True is the default and will run every interval since start_date
  • Backfill re-runs a historical range deliberately. In Airflow 3 this is scheduler-managed and visible in the UI rather than a detached CLI process
  • Bound it. A backfill over two years of daily partitions launched at full concurrency will saturate the cluster — use max_active_runs and a pool
  • Backfill only works if tasks are idempotent and derive their window from the data interval
Trigger rules
all_successThe default. Run when every upstream succeeded
all_doneRun when upstreams finish, whatever the outcome. The one to use for cleanup and notification tasks
one_success
one_failed		Run as soon as any upstream succeeds or fails
none_failed_min_one_successThe correct rule for a task that joins branches
alwaysRun regardless
Branching needs the right join rule. After a branch, the untaken path is skipped — and the default all_success treats a skipped upstream as not satisfied, so the join never runs. none_failed_min_one_success is what you want.

5  ·  WRITING DAGS — THE MODERN PATTERNS MID TaskFlow and dynamic mapping · STAFF the top-level code rule
# Airflow 3 — the airflow.sdk namespace from airflow.sdk import dag, task import pendulum @dag( # a FIXED start date, never a relative one start_date=pendulum.datetime(2026, 1, 1, tz="UTC"), schedule="0 6 * * *", # not schedule_interval catchup=False, # default is True! max_active_runs=1, default_args={"retries": 3, "retry_delay": timedelta(minutes=5)}, tags=["example"], ) def daily_pipeline(): @task def extract(**context): # use the interval, never datetime.now() start = context["data_interval_start"] end = context["data_interval_end"] return fetch_rows(start, end) @task def load(rows): # dependency is implicit write(rows) load(extract()) daily_pipeline()
The TaskFlow API is the modern way to write DAGs. Decorated functions, dependencies inferred from how values are passed, and XComs handled for you. It is far more readable than explicitly wiring operators with >>, and it is what new material assumes.
The rule that matters most: nothing expensive at module level. The DAG file is re-executed on every parse — commonly every thirty seconds, forever. A Variable.get(), a database query, an API call or a large import at module level runs every time, for every file. It slows every schedule for every DAG, and it presents as “the scheduler is slow” rather than as a problem with your file.
# WRONG — runs every 30 seconds, forever config = Variable.get("my_config") df = pd.read_csv("s3://bucket/big.csv") # RIGHT — runs only when the task runs @task def work(): config = Variable.get("my_config")
Dynamic task mapping
@task def process(f): return handle(f) # one task instance per file, decided at runtime process.expand(f=list_files())
Creates a variable number of parallel task instances from a runtime value. This replaced the old pattern of generating tasks in a loop at parse time, which forced the DAG structure to be known before the run and made parsing expensive.
Structure and organisation
  • TaskGroups for visual and logical grouping — SubDAGs are removed, and TaskGroups were always the better answer
  • One DAG per logical pipeline. Hundreds of tasks in one DAG is hard to operate and slow to parse
  • Keep tasks small and single-purpose — a failed task should be re-runnable on its own
  • Put shared logic in an importable module, not copied across DAG files
  • Set retries and retry_delay in default_args. The default of no retries is rarely what you want
6  ·  EXECUTORS where tasks actually run
ExecutorUse, and trade-offs
LocalExecutorRuns tasks as subprocesses on the scheduler host. Simple, genuinely useful, and correct for small production deployments. Bounded by one machine, and now the answer for local development too
CeleryExecutorThe most common production choice. Distributes tasks to a pool of persistent workers via Redis or RabbitMQ. Mature and predictable; workers are always running, so you pay for idle capacity, and the broker is another component to operate
KubernetesExecutorOne pod per task. Strong isolation, per-task resources and images, and scales to zero. Pod startup adds latency per task, which hurts for many short tasks, and it requires real Kubernetes competence
EdgeExecutorAdded in Airflow 3 for distributed and edge-compute workloads where workers sit outside the core cluster
Multiple executorsRecent versions allow configuring several and choosing per DAG or per task — which supersedes the older hybrid executors
Two corrections worth noting. SequentialExecutor has been removed — LocalExecutor handles SQLite and is the local answer. And the hybrid Celery-Kubernetes executor is superseded by native multi-executor configuration, which is cleaner and does not require a special executor class.
Choosing, briefly. Small and simple → LocalExecutor. Steady load with many similar tasks → Celery. Varied resource needs, per-task dependencies, or spiky load where scale-to-zero matters → Kubernetes. Already on Kubernetes with a platform team → Kubernetes. Otherwise Celery is the lower operational burden.
The Kubernetes trade-off, precisely. Pod startup is measured in seconds. For tasks that run for minutes or hours, that is irrelevant and the isolation is worth a great deal. For thousands of tasks that each take five seconds, the overhead dominates and Celery will be dramatically better.
7  ·  DEPLOYMENT — TOPOLOGY, AND GETTING DAG FILES TO THE WORKERS MID the topologies · STAFF DAG delivery, which is the decision people skip
TopologyShape
Single node
dev and test		Everything on one host with LocalExecutor and Postgres. Fine for development, and acceptable for small production if you accept the single point of failure
Celery cluster
common production		Two or more schedulers, several API servers behind a load balancer, a triggerer, a worker fleet, a Redis or RabbitMQ broker, and a managed Postgres. The standard shape

Run more than one scheduler. Highly available active-active schedulers have been supported since Airflow 2.0, they need no leader election, and the second one removes the most obvious single point of failure. There is little reason to run only one in production.
Sizing, as a starting point
Scheduler2–4 vCPU, 4–8 GB. CPU-bound on DAG parsing, so parsing cost drives this more than DAG count
API server2 vCPU, 4 GB. Scale horizontally for many UI users
WorkerEntirely workload-dependent. Size from what tasks actually do, and remember that if tasks only trigger external systems these can be small
TriggererModest — one process handles thousands of concurrent deferrals
Metadata DB4+ vCPU, 8+ GB, fast disk. Highly available. The most important component to get right
The decision most deployment guides omit: how do DAG files reach every component? The scheduler, the DAG processor and every worker need the same files and the same Python dependencies. Getting this wrong produces the confusing failure where a DAG is visible in the UI and its tasks fail on the worker with an import error.
MethodTrade-offs
Baked into the imageThe most reproducible. DAGs and dependencies are versioned together and a deploy is an image roll. Changing a DAG requires a deployment, which is a feature in regulated settings and friction in fast-moving ones
Git-sync sidecarA sidecar pulls from a repository on an interval. Fast iteration, no redeploy. Python dependencies still come from the image, so they can drift out of step with the DAGs
Shared volumeA network filesystem mounted everywhere. Simple, and it introduces a shared dependency and a performance risk on parse
Object storage syncUsed by several managed offerings — you upload to a bucket and it distributes
Whichever you choose, the dependency problem is the same one. A DAG importing a library the worker image lacks fails only at task runtime. Keep DAG and dependency versions moving together, and test the image the workers will actually use.
Logs
  • Configure remote logging to object storage from day one. Local logs disappear when a Kubernetes pod exits, and the UI then shows nothing for the run you most want to inspect
  • Set a retention policy on the bucket — logs accumulate indefinitely otherwise
  • The metadata database stores log references, not log content — but the task instance rows themselves still grow

Configuration precedence, which trips people up: environment variables of the form AIRFLOW__SECTION__KEY override airflow.cfg, which overrides the defaults. Environment variables are the right mechanism in containers, and they keep secrets out of a config file.
Tune parsing before adding hardware. If the scheduler is struggling, measure DAG parse time first — the fix is usually removing top-level code or raising the parse interval, not a bigger machine.
9  ·  CONCURRENCY & POOLS four limits, all applying at once
Tasks stuck in queued are almost always hitting one of these, and the confusion comes from there being four independent ceilings. The most restrictive one wins, and the UI does not tell you which.
1. parallelism whole cluster ↓ 2. max_active_tasks_per_dag one DAG ↓ 3. pool slots a named group ↓ 4. worker_concurrency one worker process # plus max_active_runs_per_dag, which limits # how many DAG RUNS may be active at once
Pools — the tool for protecting other systems
  • A named set of slots that tasks must acquire before running
  • The correct way to protect a fragile downstream — a legacy database that tolerates five concurrent connections gets a pool of five, and Airflow will never exceed it however many DAGs want to run
  • Tasks can request more than one slot, so a heavy task can consume proportionally more
  • priority_weight decides which queued task takes a freed slot first
Pools are the most under-used feature in Airflow. They convert “we overwhelmed the source system again” from a recurring incident into a configuration value — and unlike staggering schedules by hand, they keep working when the DAG count grows.
Queues, with Celery
  • Route tasks to specific worker groups — a memory-heavy task to large workers, everything else to standard ones
  • Set queue on the task, and start workers listening to matching queues
  • A queue with no listening worker means tasks queue forever, silently. Check this first when tasks never start
The diagnostic order for a stuck task: is the pool full, is the DAG at its task limit, is the cluster at parallelism, are workers alive and listening to the right queue? In that order — it resolves nearly every case quickly.
10  ·  XCOM, VARIABLES & CONNECTIONS and their limits
XCom — small messages only
XComs are stored in the metadata database, which sets the rule: pass references, never payloads. A path, an identifier, a row count or a status is correct. A dataframe, a file's contents or a large JSON document is not — it bloats the database, slows every scheduler query, and can exceed the column limit outright.
# WRONG return df # megabytes into the DB # RIGHT df.to_parquet(path) return path # a reference
  • A custom XCom backend can transparently store values in object storage and pass a pointer — the right answer when passing larger objects is genuinely needed
  • TaskFlow uses XComs automatically for return values, so the same size discipline applies to what your functions return
  • XCom pickling was removed in Airflow 3 — values must be JSON-serialisable, or handled by a custom backend
Variables
  • Key-value configuration stored in the database or a secrets backend
  • Never call Variable.get() at module level — it runs on every parse of every file, hammering the database. Inside a task, or via a Jinja template, is correct
  • Use a single JSON variable for related settings rather than many separate ones, to reduce lookups
Connections
  • Credentials and endpoints for external systems, referenced by conn_id
  • Encrypted at rest with the Fernet key — which must be set and safely stored, or existing connections become unreadable
  • Prefer a secrets backend — AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager. Connections then live where the rest of your secrets live, with rotation and audit
  • Never put credentials in DAG code. It is version controlled, and it is parsed and logged
11  ·  SENSORS & DEFERRABLE OPERATORS the classic resource trap
The classic Airflow outage: sensor deadlock. A sensor in its default mode occupies a worker slot for its entire wait. Schedule twenty sensors waiting on files that arrive at midday, with sixteen worker slots, and every slot is consumed by tasks doing nothing — including the tasks that would satisfy them. The cluster is fully utilised and completely stuck.
The three approaches, in increasing order of correctness
ModeBehaviour
poke
the default		Holds the worker slot and checks on an interval. Fine only for short waits measured in seconds or a few minutes
rescheduleReleases the slot between checks and returns to the queue. Far better for long waits; each check still costs a task startup, so a short poke interval is wasteful
DeferrableThe right answer. The task suspends entirely and its wait is handled by the triggerer as an async coroutine. Occupies no worker slot at all, and one triggerer handles thousands of concurrent waits
Prefer deferrable operators for anything that waits — a sensor, a long-running external job, an API poll. Most major providers ship deferrable variants. This is the single highest-value change available to a cluster whose workers are always busy but whose throughput is low.
The triggerer must actually be deployed. If it is not running, deferrable operators defer and never resume — tasks sit indefinitely with no error. Check for a triggerer before debugging anything else when a deferred task appears stuck.
Better still: do not wait at all
  • Asset-based scheduling — trigger on data being produced rather than polling for it
  • Event-driven triggers — Airflow 3 can watch external assets, such as a message queue, and start a DAG on the event
  • Always set a timeout on any sensor. A sensor with no timeout waits forever, and will still be waiting weeks later
12  ·  OPERATIONS — KEEPING IT HEALTHY OVER YEARS STAFF metadata database maintenance, parse-time budgets, and the 2 to 3 upgrade
The metadata database grows forever, and nobody notices until it is a problem. Task instance rows, log references, XComs, DAG run records and serialised DAG versions accumulate with every run. After a year of a few hundred daily tasks the tables are large enough that every scheduler query and every UI page slows down. It presents as “Airflow got slow”.
# run this on a schedule, from the start airflow db clean --clean-before-timestamp <date> # preview first airflow db clean --dry-run --clean-before-timestamp <date>
Schedule it, keep a retention window you actually need, and take a backup first. Ninety days is a common choice. Pair it with a vacuum or equivalent so the space is genuinely reclaimed — deleting rows in Postgres does not shrink the table on its own.
DAG parse time is a budget
  • Measure it — airflow dags report shows per-file parse duration
  • The usual cause of slowness is top-level code, not DAG count
  • Raise min_file_process_interval if parsing is the bottleneck and you can accept slower pickup of edits
  • Raise parsing_processes for many files
  • Keep non-DAG Python out of the DAGs folder, or use .airflowignore
Upgrading from Airflow 2 to 3
  • It is a genuine migration, not a version bump. Budget for it properly
  • Audit for removed features first — SubDAGs, SequentialExecutor, SLAs, execution_date, schedule_interval, pickling
  • Move imports to airflow.sdk for DAG constructs
  • Upgrade to the latest 2.x first, resolve every deprecation warning, then move
  • Test on a copy of the metadata database, and time the migration — on a large, uncleaned database it can be long
  • Clean the database before migrating. Less data means a faster and safer migration
  • Check provider compatibility for every provider you depend on
Routine practices
  • Rolling restarts — schedulers are active-active, so restart one at a time
  • Watch scheduler heartbeat. A scheduler that has stopped heartbeating is the most urgent alert here
  • Set log retention on the remote store
  • Pin provider versions and upgrade deliberately — providers release independently of core
  • Keep a staging environment that matches production, including the worker image
Zombie tasks — a task whose worker died without reporting state. The scheduler detects and fails them after a threshold. Frequent zombies mean workers are being killed, usually by memory limits, and the real fix is task memory or worker sizing rather than the detection setting.
13  ·  SECURITY it runs arbitrary code
Start from what Airflow actually is: a system that executes arbitrary Python with access to every credential your pipelines use. Write access to the DAGs folder is equivalent to code execution with those credentials. Treat it with the seriousness that implies.
The controls
  • Role-based access control — built in, with roles down to per-DAG permissions. Never leave authentication disabled, and never expose the UI publicly
  • Integrate with your identity provider — LDAP, OAuth, SAML or OIDC — rather than managing local users
  • A secrets backend so credentials live in Vault or a cloud secrets manager, not in the metadata database
  • Set the Fernet key and manage it as a secret. It encrypts connection passwords at rest
  • Never put secrets in DAG code. It is in version control, parsed repeatedly, and may appear in logs
  • Least privilege for the credentials Airflow holds — a task that reads one table needs read on one table
  • Review DAG folder write access as production code access, because that is what it is
  • Enable audit logging and retain it
STAFF Airflow 3 improved this structurally. The Task Execution API means tasks no longer connect directly to the metadata database. Previously any task could in principle read every connection and variable in the system; now task execution is isolated behind an API, which is a real reduction in blast radius and the main security argument for upgrading.
Multi-tenancy remains limited. RBAC restricts what users see and trigger in the UI, but tasks from different teams share workers and their credentials. For genuine isolation between untrusted teams, run separate deployments — this is what managed platforms do, and it is the honest answer.

Airflow emits metrics via StatsD, and increasingly via OpenTelemetry — feed them to Prometheus, Datadog or equivalent. The built-in UI is for inspection, not alerting; a dashboard nobody is watching at 03:00 is not monitoring.
Alerting on the right thing
  • Alert on a dataset being late, not only on a task failing. A DAG that never started produces no failure and no alert — which is the more dangerous case
  • Use callbacks — on_failure_callback and on_success_callback — to route to your paging system rather than email alone
  • Route per DAG to the owning team, not to a shared inbox nobody reads
  • Note that SLAs were removed in Airflow 3 — implement freshness expectations with external monitoring or callbacks instead
  • Suppress alert storms. One upstream failure can fail fifty downstream tasks; alert on the root, not on every consequence
Testing DAGs
  • Import test in CI — parse every DAG and assert there are no import errors and no cycles. This alone catches most broken deploys and takes minutes to set up
  • Assert structure — expected task count and dependency relationships
  • Unit test the logic, which should live in importable functions rather than inside operators
  • airflow dags test runs a DAG for a logical date locally, end to end
  • airflow tasks test runs a single task without recording state — the fastest inner loop
  • Check parse time in CI and fail the build if a DAG exceeds a threshold
CI/CD for pipelines
  1. DAGs in version control, reviewed like any other code
  2. Lint and import-test on every pull request
  3. Build the worker image with pinned dependencies, and test against it
  4. Deploy to staging that matches production, including the image
  5. Promote deliberately — image roll or git-sync from a release branch
  6. Keep DAG and dependency versions together, so a DAG never lands ahead of the library it needs
The import test is the highest return on effort available. A DAG with a syntax or import error does not merely fail — it may not appear at all, and the scheduler carries on quietly without it. Catching that in CI prevents the failure mode where a pipeline has silently not run for a week.

Note the order. None of the top four are solved by adding workers. They are parse hygiene, configuration, task design and maintenance — all visible in advance if anyone is measuring them.
Degradation
  • Webserver down — you lose visibility and manual control. Scheduling and execution continue. Not an emergency
  • One scheduler down — no impact if you run two. This is the argument for running two
  • All schedulers down — nothing new is scheduled; running tasks finish. Silent, so alert on the heartbeat
  • Workers down — tasks queue and resume when capacity returns, provided the queue and broker survive
  • Metadata database down — total outage. Every component depends on it, which is why it must be highly available
