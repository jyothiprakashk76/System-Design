One entry point for API traffic — what belongs in it, what must never, and how it fails

1  ·  WHAT AN API GATEWAY IS — AND WHAT IT IS CONSTANTLY CONFUSED WITH start here — the definitions, the neighbouring components, and the one rule that keeps a gateway healthy
The definition
An API gateway is a reverse proxy that owns the cross-cutting concerns of API traffic — authentication, rate limiting, routing, observability — so that each service behind it does not have to implement them separately.
The problem it solves, stated as arithmetic. With 40 services, doing auth, rate limiting, request logging, CORS and TLS in each one means 40 implementations, 40 sets of bugs, and 40 places to change when a policy changes. Centralising them makes it one — and that consistency, more than any single feature, is the reason gateways exist.
The one rule
The gateway handles concerns that are the same for every service. Nothing else. The moment it contains logic that is true for only one service, it has become a shared component that every team must change and no team owns — and it will be the slowest part of your delivery process within a year.
North-south, not east-west
  • North-south — traffic entering the system from outside. This is the gateway's job
  • East-west — service-to-service traffic inside the boundary. This is a service mesh's job
  • Routing internal calls through the gateway adds a hop, a bottleneck and a failure domain for no benefit
The components it is confused with
ComponentDoes
Load balancerDistributes connections across identical backends. L4 knows ports; L7 knows HTTP. Little or no policy
Reverse proxyTerminates TLS, serves static content, forwards requests. The substrate a gateway is built on
API gatewayA reverse proxy plus API concerns — authN/authZ, quotas, keys, transformation, versioning, per-consumer metering
Ingress controllerThe Kubernetes-native form of the same idea, configured by cluster resources
Service meshProxies beside every service for east-west traffic: mTLS, retries, traffic splitting, telemetry
BFFA backend per client type, owned by that client's team. Contains product logic — which is exactly why it is not the gateway
CDN / WAFSits in front of the gateway: caching, DDoS, bot defence, TLS at the edge
Most large systems run several of these, not one. CDN and WAF at the edge, a gateway for north-south policy, a mesh for east-west, and a BFF per client where the shaping genuinely differs. Choosing between them is a category error; the question is which concern belongs where.
What belongs in a gateway
YesNo
TLS terminationBusiness rules or validation beyond schema
Authentication and token validationData enrichment from databases
Coarse authorisation — is this token allowed here at allFine-grained, resource-level permission checks
Rate limiting and quotasOrchestrating multi-step workflows
Routing, canary and traffic splittingAnything specific to one service
Request and response transformationHeavy aggregation across many services
Schema validation, CORS, compressionRetries that hide a broken upstream
Correlation ids, metrics, access logsState that makes the gateway non-restartable
The test to apply to any proposed feature. Would every service behind the gateway need this identically? If yes, it belongs there. If it is true for one service, or it needs to read that service's data to decide, it belongs in the service.
Availability arithmetic. Every request now traverses one more component, so the gateway's availability multiplies with everything behind it. It must be stateless, horizontally scaled and deployed across zones — otherwise you have centralised a single point of failure along with the policy.

3  ·  ROUTING matching, rewriting, shifting
What a route can match on
Hostapi.example.com vs partner.example.com — often the first split
PathPrefix, exact, or regex. Prefer prefix and exact; regex routes are slow to evaluate and hard to reason about
MethodLets read and write traffic take different policies
HeaderAPI version, tenant, client type, feature flag
WeightPercentage splits for canary and blue/green
Precedence must be explicit. When two routes could match, the winner should be decided by a documented rule — usually most-specific-wins — not by declaration order in a file that several teams edit. Ambiguous precedence produces routing that changes when an unrelated team adds a rule.
Rewriting, carefully
# external contract stays stable… /v1/orders/{id} → order-service:8080/orders/{id} # …while the internal shape changes freely /v1/orders/{id} → order-service-v2:8080/api/orders/{id}
This indirection is one of the gateway's most valuable properties. Services can be renamed, split, merged or reimplemented without any client changing a URL — which is what makes a strangler migration practical.
Kubernetes: Ingress and Gateway API
  • Ingress — the original resource. Simple, and its limitations pushed almost every capability into vendor-specific annotations
  • Gateway API — the successor, with a role-oriented split: cluster admins own the GatewayClass, platform teams own Gateway, application teams own HTTPRoute. GatewayClass, Gateway and HTTPRoute are GA; some route types remain experimental
  • They coexist. Most controllers support both, so migration is incremental — new services on HTTPRoute, existing Ingress untouched
The role separation is the real advance. It is what lets application teams self-serve routes without being able to change TLS, listeners or which routes are permitted — the exact bottleneck that makes a shared gateway painful.
4  ·  AUTHENTICATION & AUTHORISATION what the gateway can decide, what it must not, and the failure that turns a gateway into a vulnerability
Mechanisms, and where each fits
MechanismCharacter
API keyIdentifies an application, not a user. Simple, and it is a long-lived shared secret — fine for metering, weak as authentication
JWT validationVerify the signature locally against the issuer's public keys. Stateless and fast — no network call per request
Token introspectionAsk the authorisation server whether the token is still valid. Accurate, and it adds a synchronous dependency to every request
OAuth 2.x / OIDCThe standard for delegated access. The gateway is the resource server
mTLSCertificate-based. Strong, and it suits partner and server-to-server traffic
The stateless-versus-revocable trade-off. Local JWT validation is fast but a token stays valid until it expires — you cannot revoke it. Introspection is revocable but puts the authorisation server in the path of every call. The usual resolution is short-lived tokens plus introspection or a revocation list only for high-value operations.
Validating a JWT properly
  • Pin the accepted algorithms. Never trust the alg header — accepting none, or letting an attacker downgrade RS256 to HS256, is a classic and still-seen bypass
  • Verify issuer and audience, not only the signature. A valid token for a different service is still a valid token
  • Cache the JWKS, and handle key rotation by kid. Refetch on an unknown key id, with a rate limit so rotation cannot become a stampede against the identity provider
  • Allow small clock skew on expiry, and no more
  • Check scopes against the route
The single most important rule on this panel. The gateway performs coarse authorisation — is this token valid, and is this route permitted for its scopes. It cannot perform fine-grained authorisation, because “may this user read this order?” requires the order service's own data. Any design where the gateway is the only authorisation point is one internal call, one misconfigured route, or one alternative ingress away from full exposure.
Defence in depth, concretely
LayerDecides
GatewayIs the token genuine, unexpired, and does its scope cover this route at all?
ServiceDoes this subject own or have rights to this resource? Re-derived from the token, never from a request parameter
Data layerTenant filter on every query, and a test proving cross-tenant access fails
Identity propagation. The gateway forwards the verified identity in a signed header or, better, exchanges the client token for a downscoped internal token bound to a single audience. That way a compromised internal service holds a credential valid for one hop, not for everything.
The header-stripping requirement
# the gateway MUST remove these if a client sent them X-User-Id: 1 ← attacker-supplied X-Tenant-Id: acme X-Internal-Auth: true # then set them itself, from the verified token X-User-Id: u_8813 (derived, trusted) X-Correlation-Id: req_…
Forgetting to strip is a full authentication bypass, and it is a recurring vulnerability class rather than a theoretical one. Deny-list is the wrong approach here — build the forwarded header set explicitly from the verified context, and drop everything else in that namespace.
5  ·  RATE LIMITING, QUOTAS AND LOAD SHEDDING the algorithms, what each actually guarantees, and the distributed-counter decision nobody documents
The algorithms
AlgorithmBehaviour · trade-off
Fixed windowCount per calendar window. Trivial and memory-light. Allows a double burst at the boundary — the tail of one window plus the head of the next
Sliding window logStore a timestamp per request. Exact, and the memory cost scales with traffic
Sliding window counterWeighted blend of the previous and current window. Approximate, cheap, no boundary burst. The usual practical choice
Token bucketTokens refill at a steady rate; a request costs one. Permits bursts up to the bucket size — usually what you want for a public API
Leaky bucketRequests drain at a fixed rate. Smooths output and protects a fragile upstream, at the cost of queueing latency
Choose by what you are protecting. Token bucket when clients legitimately burst and the upstream can absorb it. Leaky bucket when the upstream cannot — a legacy system with a fixed connection pool, for instance. Sliding window counter when you simply want a fair, cheap, general-purpose limit.
Dimensions to limit on
  • Per API key or client — the commercial dimension, and what quotas are billed against
  • Per user — fairness within one client application
  • Per tenant — stops one customer starving the others
  • Per route — an expensive endpoint deserves a tighter limit than a cheap one
  • Per IP — only useful before authentication, and weak behind NAT or a proxy
Rate limit and quota are different things. A rate limit is short-term protection — requests per second. A quota is a commercial allowance — calls per month. They are enforced differently, breached differently, and should return different errors.
Distributed counting — the part usually skipped
With many gateway replicas, “100 requests per second” needs shared state. Three approaches, and the choice has real consequences:
ApproachTrade-off
Local onlyNo coordination, no latency. Actual limit is n × the configured value, and it moves as replicas scale
Central storeAccurate. Adds a network call per request and makes the store a hard dependency of every API call
Local + async syncApproximate but close, with no per-request latency. What most production gateways actually do
The decision nobody writes down: fail open or fail closed? If the counter store is unreachable, do you allow traffic through unlimited, or reject everything? Fail open risks overwhelming upstreams during exactly the incident that took the store down. Fail closed turns a rate-limiter outage into a total API outage. Most choose fail open with a conservative local fallback limit — but it must be a decision, made in advance and written down.
Telling the client what happened
HTTP/1.1 429 Too Many Requests Retry-After: 12 RateLimit-Limit: 1000 RateLimit-Remaining: 0 RateLimit-Reset: 12 { "code": "RATE_LIMIT_EXCEEDED", "message": "1000 req/min exceeded for this key", "requestId": "req_8f3c" }
Return the headers on successful responses too, not only on rejection. A well-behaved client can then slow down before being limited — which is far better for both sides than discovering the limit by hitting it.
Load shedding is a different tool. Rate limiting enforces an agreed contract per client; load shedding protects the system when it is genuinely overloaded, by rejecting the lowest-value traffic regardless of whose limit it is within. You need both, and they should be tuned independently.
6  ·  CACHING & PERFORMANCE where the milliseconds are
What is safely cacheable
GoodPublic reference data, catalogues, configuration, anything identical for all callers
CarefulPer-user responses — only with the identity in the cache key, and a short TTL
NeverAnything that mutates state, and anything whose authorisation could change between requests
The cache-key mistake that leaks data. Omit the identity or tenant from the key and one user's response is served to another. It is the highest-severity bug a gateway can have, it is invisible in testing with a single account, and it is found by customers. Include every dimension the response varies on — and test with two accounts.
Connection handling
  • Keep-alive to upstreams — a fresh TCP and TLS handshake per request is pure added latency
  • Bounded connection pools per upstream, so one slow service cannot consume every connection
  • HTTP/2 to backends for multiplexing; be aware that one connection then carries many streams and a stall affects all of them
  • Stream rather than buffer large payloads — buffering a 100 MB upload in the gateway is memory you did not budget for
Watch these
  • Gateway-added latency, measured separately from upstream time — the only way to know whose problem it is
  • Any synchronous external call in the request path; each one adds its p99 to yours
  • Regex-heavy route tables, evaluated per request
  • Response compression cost — sometimes it is cheaper not to
The realistic target is single-digit milliseconds added at p50 and a tight p99. If the gateway is contributing more than that, look for a network call in the filter chain before looking at CPU.
7  ·  RESILIENCE and how it backfires
ControlPurpose · setting
TimeoutPer route, not one global value. A report endpoint and a health check have nothing in common
RetryIdempotent methods only, with backoff and jitter. Two attempts, not five
Circuit breakerStop calling an upstream that is already failing; fail fast instead
Outlier detectionEject a single unhealthy instance from the pool rather than failing the whole route
BulkheadCap concurrency per upstream so one cannot exhaust the gateway's capacity
Load sheddingReject early under overload, preserving capacity for what matters most
Retry amplification is the classic gateway-caused outage. The client retries three times, the gateway retries three times, and the service mesh retries three times — 27 requests arrive at a service that is already struggling, and the retries themselves keep it down. Decide which single layer owns retry, and disable it explicitly everywhere else.
A retry budget is better than a retry count. Cap retries at a small percentage of total traffic, so retries cannot exceed a fraction of load no matter how many requests are failing. This is what stops a partial outage becoming a full one.
Health checking
  • Active — the gateway probes upstreams on a schedule
  • Passive — it observes real responses and ejects hosts that fail. Cheaper and faster to react
  • Do not fail a readiness check because a downstream is down, or one dependency's outage removes every gateway replica simultaneously
Degrade rather than fail where the domain allows. A stale cached response, an empty list, or a partial payload is usually better than a 502 — but this must be an explicit per-route decision, not an accident of configuration.
8  ·  OBSERVABILITY the best vantage point you have
Every external request passes through the gateway, which makes it the one place that sees all API traffic. It is the cheapest and most complete telemetry in the system.
What to emit
  • Access log — route, status, latency, upstream, consumer, bytes, and the request id
  • RED metrics per route — rate, errors, duration, at percentiles
  • A span per request, with the trace context propagated to the upstream
  • Correlation id — accept the client's if present, generate one if not, and always return it in the response
The mistake that quietly ruins a metrics bill: cardinality. Labelling metrics with the raw path means /orders/1, /orders/2 and a million more become a million time series. Always label with the route template — /orders/{id} — never the resolved path. The same applies to user id, request id and any unbounded value.
What to alert on
5xx rate per routeThe primary signal that something broke
4xx spikeUsually a client deploy, a contract change or an attack
401/403 spikeKey rotation gone wrong, or credential stuffing
429 rateA limit set too tight, or genuine abuse — the two look identical without context
Gateway-added latencyIsolates gateway problems from upstream ones
Config version skewReplicas running different configurations is a real and confusing failure
Sample traces, log every request. Full tracing at high volume is expensive and rarely proportionate; access logs are cheap and complete. Sample traces at a few percent, and raise the rate for errors and slow requests where the detail actually helps.
9  ·  VERSIONING & CONTRACTS the promise to consumers
Where the version goes
StyleTrade-off
Path
/v1/orders		Explicit, cacheable, obvious in logs and dashboards. The pragmatic default
HeaderKeeps URLs clean; harder to debug, and easy to omit by accident
Content negotiationFormally correct, and unfamiliar to most consumers
Version the contract, not the implementation. A new internal service version does not need a new API version — the gateway's rewriting is exactly what lets those change independently. Bump the API version only when the consumer-visible contract breaks.
Breaking versus non-breaking
  • Safe — adding an optional field, adding an endpoint, adding an enum value if clients tolerate unknowns
  • Breaking — removing or renaming a field, tightening validation, changing a type, changing a status code, altering pagination
  • Silently breaking — changing default behaviour, or the meaning of an existing field. The worst kind, because nothing errors
Deprecating properly
  • Announce with a date, and return Deprecation and Sunset headers so it is discoverable from the response itself
  • Know who is calling — per-consumer metrics per version is what makes a retirement decision possible
  • Contact the remaining callers individually; a changelog nobody reads is not a migration plan
  • Brownout before switch-off — return errors for short windows to surface the dependency while it is still recoverable
Validate against the schema at the edge. Rejecting malformed requests at the gateway means every service behind it can assume well-formed input — and OpenAPI then becomes an enforced contract rather than documentation that drifts.
10  ·  OPERATING IT — OWNERSHIP, BLAST RADIUS AND THE ORGANISATIONAL FAILURE the part that decides whether a gateway accelerates delivery or becomes the thing everyone waits on
The organisational failure mode
A shared gateway with a central owning team becomes a bottleneck, and it happens gradually enough that nobody notices until it is severe. Every new route, every limit change and every header tweak becomes a ticket to one team, who are also on call for it. Delivery for forty teams throttles to the throughput of one.
What fixes it
  • Self-service within guard rails. Teams own their own routes; the platform team owns the listeners, TLS, defaults and what is permitted
  • Policy as code, reviewed in the owning team's repository — not a form request into a queue
  • Validation in CI that catches conflicts, unreachable rules and missing upstreams before merge
  • Sensible defaults so the common case needs no decision — a route with no explicit timeout still gets one
This is precisely what the role-oriented split in Kubernetes Gateway API encodes — cluster admin, platform team and application team as distinct resources with distinct owners. The idea works outside Kubernetes too, and is worth adopting whatever the product.
Blast radius — the thing to design against
ChangeReaches
One service's routeThat service. Acceptable
A shared plugin or filterEvery route using it
Global configurationEvery API, simultaneously
A gateway version upgradeEverything, including behaviour you did not know you relied on
Because of that last row, the gateway itself must be deployed like a risky service: canary a small percentage of traffic, watch error rate and latency, and roll back automatically. Upgrading a gateway in place across all replicas is one of the more reliable ways to cause a total outage.
Shared or dedicated?
One shared gatewayConsistent policy, one thing to operate, one place to look. And one blast radius, one bottleneck, one upgrade that affects everyone
Per-domain gatewaysIsolation and independent change. More to run, and policy drifts between them unless the configuration is generated from something common
A common middle path is a shared gateway product and configuration standard, deployed as separate instances per domain or criticality tier — so public, partner and internal traffic cannot take each other down while the policy stays uniform.
Multi-tenancy and isolation
  • Separate listeners for public, partner and internal traffic; different policy, different exposure, different limits
  • Per-tenant rate limits, so one customer's burst cannot degrade another's service
  • Per-upstream connection pools, so a slow backend cannot consume gateway capacity that other routes need
  • Consider dedicated capacity for the highest-value traffic — a checkout path should not queue behind a partner's bulk export
Capacity and scaling
  • Scale on connections and CPU, not request rate alone — long-lived connections and streaming change the shape entirely
  • Watch file descriptors and connection limits; they bind before CPU does
  • Pre-scale for known events. Autoscaling reacts after the queue has already built
  • Load test the gateway separately from the services, or you cannot attribute the limit
What breaks first, in order. Connection and file-descriptor limits, then any synchronous external call in the filter chain, then TLS handshake CPU under a connection storm, then the rate-limit store, then raw throughput. Only the last is solved by adding replicas — the rest are configuration and design.
11  ·  ANTI-PATTERNS AND PRODUCTION FAILURES how a gateway goes from useful to load-bearing in the worst sense
Design anti-patterns
Anti-patternWhy it hurts
Business logic in the gatewayThe one to refuse first. Logic that belongs to a service ends up owned by no team, tested by nobody, and deployed on someone else's schedule
Heavy aggregationOne request fanning out to eight services makes the gateway a distributed monolith with the worst availability in the system. If a client needs a composed view, that is a BFF owned by the client team
Sole authorisation pointAny path that bypasses the gateway — an internal caller, a second ingress, a misconfiguration — is unauthenticated access
Doing the mesh's jobRouting east-west traffic through the gateway adds a hop and a shared failure domain for no benefit
Stateful gatewaySession affinity or local accumulation prevents free scaling and restarts, which is the property that made it safe
Live editingAn admin UI that applies changes instantly guarantees an unreviewed change reaches production
Production failures
FailureWhat you see & the fix
Bad config pushEvery API fails at once. Validate in CI, roll out progressively, roll back automatically
JWKS fetch failureAll authentication fails after a key rotation. Cache keys, refresh proactively, tolerate a stale cache briefly
Rate-limit store downEither unlimited traffic or none. Decide fail-open versus fail-closed in advance, with a local fallback
Retry amplificationA struggling service is kept down by retries. Retry budget, and one owning layer
Connection exhaustionNew requests refused while CPU is idle. Raise limits, bound pools per upstream, tune keep-alive
Cardinality explosionMetrics cost and query time both spike. Label with route templates, never raw paths
Cache key omissionOne user receives another's data. Include identity in the key; test with two accounts
The questions to be ready for
·“Is the gateway a single point of failure?” Structurally yes, which is why it is stateless, multi-replica, multi-zone, fronted by a load balancer, and holds last-known-good config so a control-plane outage does not stop traffic
·“Why not put auth in every service?” You still do — the gateway does coarse validation for consistency and early rejection; services do fine-grained authorisation because only they hold the data to decide
·“Gateway or service mesh?” Different traffic. North-south versus east-west. Large systems run both
·“Would you build one?” Almost never. The proxy is the easy part; the control plane, hot reload, observability and edge cases are years of work that mature products have already done
·“What would you remove?” Aggregation, any business logic, and any synchronous external call in the filter chain
The summary worth ending on. A gateway is valuable exactly in proportion to how boring it is. Uniform policy, no per-service special cases, no logic that needs testing, and a configuration that teams change themselves. The moment it becomes interesting, it has become a distributed monolith at the front door of the system.

The honest position on building your own. Writing a proxy that forwards a request is a weekend. Writing hot configuration reload, graceful draining, connection pooling, retry budgets, distributed rate limiting, JWKS rotation, TLS management, per-route observability and the operational tooling around all of it is several years — and every one of those is a place to get it subtly wrong in production. Adopt a product, and spend the effort on the configuration and the ownership model instead, which is where the outcomes actually differ.
13  ·  READINESS CHECKLIST before a gateway sits in front of production traffic
☐ Data plane is stateless, multi-replica and spread across zones
☐ Serves last-known-good config when the control plane is unreachable
☐ No synchronous config read in the request path
☐ Configuration is version-controlled and reviewed like code
☐ Config validated in CI — schema, route conflicts, unreachable rules, missing upstreams
☐ Config rollout is progressive, with automatic rollback
☐ Gateway upgrades canaried, never applied in place to all replicas
☐ Route precedence documented and deterministic
☐ Timeout set per route, derived from measurement
☐ Retries only on idempotent methods, with backoff and jitter
☐ One layer owns retry; a retry budget caps amplification
☐ Circuit breaker and outlier detection configured per upstream
☐ Connection pools bounded per upstream
☐ Readiness does not fail because a downstream is down
☐ Connection draining on shutdown, verified under load
☐ JWT algorithms pinned; alg header never trusted
☐ Issuer and audience verified, not only the signature
☐ JWKS cached with rotation by kid, and refetch rate-limited
☐ Client-supplied identity headers stripped before forwarding
☐ Forwarded headers built from verified context, allow-listed not deny-listed
☐ Services re-authorise — the gateway is not the only check
☐ Cross-tenant access test exists and passes
☐ Rate limits per key, user, tenant and route
☐ Fail-open vs fail-closed decided for the limiter store, and documented
☐ Rate-limit headers returned on success as well as on 429
☐ Quotas distinguished from rate limits, with different errors
☐ Load shedding configured independently of rate limiting
☐ Cache keys include every varying dimension, identity included
☐ Cache tested with two accounts for cross-user leakage
☐ Metrics labelled with route templates, never raw paths
☐ Correlation id accepted, generated, propagated and returned
☐ Gateway-added latency measured separately from upstream
☐ Alerts on 5xx, 4xx spikes, 401/403 spikes, 429 rate and config skew
☐ Request schema validated at the edge against the published contract
☐ Deprecation and sunset headers emitted for retiring versions
☐ Per-consumer, per-version usage tracked so retirement is possible
☐ Teams self-serve routes within platform-owned guard rails
☐ Public, partner and internal traffic isolated by listener and policy
☐ Load tested independently of the services behind it
☐ No business logic, no heavy aggregation, no per-service special cases
The one that summarises the sheet: take the gateway out of the path for one route and ask what a client could now do that they could not before. If the answer is “reach the service without authentication”, the security model depends on a proxy rather than on the services — and every internal caller, second ingress and future misconfiguration is already an exposure.
