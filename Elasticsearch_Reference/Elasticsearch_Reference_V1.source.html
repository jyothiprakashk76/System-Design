1  ·  WHAT ELASTICSEARCH IS — AND THE ONE THING IT IS NOT start here — the inverted index, near-real-time, and why treating it as a system of record is the root of most trouble
The definition
A distributed search and analytics engine built on Apache Lucene. Each shard is a Lucene index; Elasticsearch adds distribution, replication, a REST API and a query language on top. Understanding that Lucene is underneath explains most of its behaviour — including the parts that surprise people.
The core data structure is the inverted index. Rather than mapping document to terms, it maps term to the documents containing it. That is why full-text search over hundreds of millions of documents returns in milliseconds — and why the text must be broken into terms first, which is what analysis does and why mappings matter so much.
Near-real-time, stated precisely
A document is not searchable the instant it is indexed. It becomes visible after a refresh, which creates a new searchable segment. The default interval is 1s.
The refinement most summaries omit. Indices that have received no search for a period become search-idle and stop refreshing on that schedule — the refresh happens when a search next arrives. So “one second” is the busy-index case, not a universal guarantee. Use ?refresh=wait_for when a write must be visible to the very next read.
The most important sentence on this sheet: Elasticsearch is not a system of record. There are no multi-document transactions, no rollback, no foreign keys, and no join in the relational sense. Visibility is delayed by design. It is a search and analytics layer over data that lives somewhere else, and it should always be rebuildable from that source.
The practical test. If losing the entire cluster means re-indexing from a database or an event log over some hours, the architecture is sound. If it means losing data that exists nowhere else, the design has a defect — and no replica count or snapshot schedule fully compensates for it.
Use it when
  • Full-text search with relevance ranking is a core requirement — this is what it is for
  • Log, metric and trace analytics over large volumes with time-based retention
  • Ad-hoc aggregation and exploration across high-cardinality, semi-structured data
  • Autocomplete, suggestions, faceted navigation, geospatial and vector similarity search
  • Read-heavy workloads where seconds of visibility delay are acceptable
Do not use it when
  • You need ACID transactions or strict consistency — it offers neither
  • It would be the only copy of the data
  • Highly relational data with frequent joins — denormalise or keep it relational
  • Frequent updates to the same documents — an update rewrites the whole document and marks the old one deleted, and the churn is expensive
  • Simple key-value lookup at very high write rates — the wrong tool by a wide margin

2  ·  MAPPINGS — THE SCHEMA YOU CANNOT CHANGE the decision that is genuinely hard to reverse · JUNIOR text versus keyword · STAFF reindex, aliases, field explosion
You cannot change the type or analyser of an existing field. The inverted index was built at index time using those settings — altering them would invalidate every term already written. Adding a new field is fine; changing an existing one requires reindexing into a new index. This is the single biggest difference from a relational schema, and planning for it is not optional.
text versus keyword — the most common mistake here
textkeyword
Analysed?Yes — broken into termsNo — stored whole
ForFull-text search, relevanceExact match, filters, sorting, aggregations
Sort / aggregateNo — needs fielddata, which is expensive and off by defaultYes — via doc values
Exact matchUnreliable — the stored terms are analysed, so a term query usually failsExact
The default handles both, and it is worth knowing why. Dynamic mapping maps a string as text with a .keyword sub-field. So title searches full-text and title.keyword sorts and aggregates. This is a multi-field, and it is why so much works without anyone defining a mapping — and why the aggregation on title that failed works when you add .keyword.
The classic confusion: match versus term. match analyses your query text the same way the field was analysed; term does not and looks for the literal value. A term query for "New York" against an analysed field returns nothing, because the index contains new and york separately.
Dynamic mapping, and where it turns dangerous
  • The first document defines the field. Whatever type is inferred is what you are committed to
  • A field arriving as "123" once becomes a string forever, and a later numeric range query on it will not work as expected
  • Set dynamic: strict on anything important, so an unexpected field is an error rather than a silent commitment
Mapping explosion — a real cause of cluster outages. If field names come from user or customer data — an object keyed by identifier, or arbitrary log attributes — every new key becomes a new mapped field. The mapping grows without limit, the cluster state grows with it, and because cluster state is replicated to every node the whole cluster degrades. There is a default limit of 1000 fields per index, and hitting it is a symptom rather than the problem.
The fix is a modelling one: store such data as an array of key/value pairs — [{k: "colour", v: "red"}] — which is two fields regardless of how many distinct keys exist. The flattened field type solves the same problem, mapping an entire object as a single field at the cost of some query flexibility.
Changing a mapping without downtime
# applications always read and write through an ALIAS PUT /_aliases { "actions": [ { "add": { "index": "orders-v1", "alias": "orders" } } ]} # 1. create orders-v2 with the corrected mapping # 2. reindex, which re-analyses every document POST /_reindex { "source": {"index": "orders-v1"}, "dest": {"index": "orders-v2"} } # 3. swap the alias atomically, then drop v1
Never point an application at a concrete index name. Always use an alias. It costs nothing on day one and is what makes every future mapping change a routine operation rather than an outage.
3  ·  TEXT ANALYSIS how text becomes searchable terms
Analysis converts a text field into the terms stored in the inverted index. It runs in three ordered stages, and it applies only to text fields — never to keyword, numbers or dates.
1. CHARACTER FILTERS strip HTML, replace chars ↓ 2. TOKENIZER split into tokens ↓ (exactly one) 3. TOKEN FILTERS lowercase, stop words, stemming, synonyms
What each stage contributes
Char filterOperates on the raw string before tokenising — removing markup, mapping characters
TokenizerExactly one. standard splits on word boundaries; keyword emits the whole input; ngram and edge_ngram produce partial-word tokens for autocomplete
Token filtersAny number, in order. lowercase makes matching case-insensitive; stop removes common words; stemmer reduces to a root so running matches run; synonym expands equivalents
Index-time and query-time analysis must be compatible. The query text is analysed with the field's search analyser and the resulting terms are looked up. If the two chains disagree — different stemming, different case handling — nothing matches, and there is no error. It simply returns zero results, which is why this is hard to diagnose without the tool below.
The _analyze API is the debugging tool for exactly this. It shows the tokens a given analyser produces, so you can compare what was indexed against what the query generates. It answers “why does this search return nothing” faster than anything else.
GET /orders/_analyze { "field": "description", "text": "Running Shoes" } → ["run", "shoe"] with a stemmer applied
Changing an analyser requires a reindex, for the same reason a type change does — the existing terms were produced by the old chain. Design the analysis alongside the mapping, and use edge_ngram or the completion suggester for autocomplete rather than wildcard queries, which cannot use the index efficiently.

5  ·  INDEXING PERFORMANCE — SEGMENTS, MERGES AND THROUGHPUT MID the knobs that matter · STAFF what each one actually trades away
The levers, in the order worth trying
LeverEffect, and the cost
Use the bulk APIThe single largest win. Around 5–15 MB per request as a starting point, tuned by measurement. Never index documents one at a time at volume
Raise refresh_intervalFewer segments created and merged. Costs visibility delay — set to 30s for logs, or -1 during a bulk load and restore afterwards
Index with zero replicas, then addOnly for an initial load into an empty index. No redundancy while it runs
Let Elasticsearch assign idsA supplied id forces a check for an existing document; an auto-generated one skips it
Fewer, larger shardsLess coordination and merge overhead per document
Map only what you queryDisable indexing on fields never searched, and doc_values on fields never sorted or aggregated
Faster storageMerging is I/O bound. Local SSD or NVMe makes a larger difference than most tuning
Do not use async translog durability by default. It is a genuine speed-up and it introduces a window in which acknowledged writes can be lost on a crash. Acceptable for logs where the source can replay; unacceptable for anything else.
Segments and merging
  • Every refresh creates a segment. Many small segments slow search, because each is consulted separately
  • Merging runs continuously in the background, combining small segments and physically dropping deleted documents
  • Merging competes with indexing and search for I/O — a heavy ingest period will show elevated merge activity and latency
  • Deleted documents occupy space until merged. A high delete or update rate means a persistently inflated index
force_merge is for read-only indices only. Merging a finished time-based index down to one segment is a genuine and worthwhile optimisation. Running it on an index still receiving writes produces very large segments that future merges struggle with, and the effect is long-lived. The rule is simple: only force-merge an index that will never be written to again.
Rejections and backpressure
  • Write thread pools have bounded queues. When full, requests are rejected — this is deliberate backpressure, not a failure to fix by enlarging the queue
  • Rejections must be retried with backoff by the client. Most official clients and Logstash do this; hand-written ingest often does not, and silently drops data
  • A rising rejection count means the cluster cannot keep up — the answer is more nodes, better storage, or less work per document, not a bigger queue
Check bulk responses per item. A bulk request returns HTTP 200 while individual items failed. Code that checks only the status code loses documents silently — one of the most common and least visible ingest bugs in production.
6  ·  SHARD SIZING the number to get right first
Primary shard count is fixed when the index is created. It cannot be changed in place, because the shard for a document is derived from a hash of its id. Splitting and shrinking exist, and both write a new index. In practice, plan it — or use rollover so each new index gets a fresh decision.
The guidance, and what it is based on
10–50 GB per shardThe widely used working range. Smaller wastes overhead; much larger slows recovery, relocation and merges
Around 20 shards or fewer per GB of heapPer node. A node with 30 GB of heap should stay under roughly 600 shards, and comfortably below that in practice
Shards ≥ nodesFewer shards than data nodes leaves nodes idle for that index
# worked example: 2 TB of log data, 30-day retention daily volume ≈ 2 TB / 30 ≈ 68 GB/day target shard size ≈ 40 GB primaries per day ≈ 68 / 40 ≈ 2 with 1 replica → 4 shards/day over 30 days → 120 shards total # the wrong instinct — 5 primaries per day "for speed" → 300 shards of ~14 GB each: more overhead, more merging, slower searches. Not faster.
Oversharding is the classic mistake, and it is usually well-intentioned. More shards feels like more parallelism. But each shard is a full Lucene index with fixed overhead, and every search must coordinate across all of them. Past the point where shards are large enough to be efficient, adding shards makes the cluster slower and less stable, not faster.
For time-based data, use data streams with rollover rather than deciding a shard count once and living with it. Rollover creates a new backing index at a size or age threshold, so each index is sized against actual volume — and retention becomes dropping whole indices, which is nearly free, instead of deleting documents, which is expensive.
7  ·  QUERYING AND RELEVANCE JUNIOR the query types · MID filter context · STAFF how scoring actually works
The query types worth knowing
QueryBehaviour
matchAnalyses the input, then looks for the resulting terms. The default choice for full-text
termDoes not analyse. Exact term lookup — correct on keyword, and a common source of empty results on text
match_phraseTerms in order and adjacent
multi_matchOne query across several fields, with per-field weighting
boolCombines clauses: must, should, filter, must_not. The workhorse
rangeNumeric, date and other ordered types. Almost always belongs in filter context
wildcard / regexpExpensive. A leading wildcard cannot use the index at all — use edge_ngram instead
knnVector similarity search over dense vectors — semantic search and retrieval for language models
The optimisation to apply everywhere: move yes-or-no conditions into filter. They then skip scoring entirely and their results are cached and reused across queries. A status, a tenant id, a date window and a category all belong there. This is frequently the largest single improvement available to a slow search, and it changes no behaviour.
How relevance is calculated
  • BM25 is the default similarity. Three intuitions drive it: a term appearing more often in a document scores higher; a term appearing in fewer documents overall is more discriminating and worth more; and a match in a shorter field counts for more than the same match in a long one
  • Scores are relative to one query and are not comparable between queries or across indices. A score of 8 means nothing on its own
  • explain shows the full scoring breakdown for a document — the way to answer “why is this result ranked third”
  • Boosting weights fields or clauses; function_score and rank_feature fold in signals like recency or popularity
STAFF Why scores can look wrong on a small index. Term statistics are per shard, not cluster-wide. With few documents unevenly distributed, the same term can score differently depending on which shard holds it, and results appear mis-ranked. dfs_query_then_fetch gathers global statistics first and fixes it, at the cost of an extra round trip. The effect disappears naturally as documents accumulate — so it is mostly a test-environment surprise.
Getting relevance right is an iterative, measured activity, not a configuration setting. Build a judgement set of queries with expected results, change one thing, and measure. Tuning boosts by intuition until a few examples look right reliably makes other queries worse without anyone noticing.
Modern retrieval combines both. Keyword search via BM25 and vector search via knn have complementary failure modes — lexical matching misses paraphrase, semantic matching misses exact identifiers. Hybrid retrieval that combines both rankings is the current practice for search backing language-model applications.
8  ·  AGGREGATIONS and their approximations
FamilyPurpose
MetricA value over a set — avg, sum, min, max, percentiles, cardinality
BucketGroups documents — terms, date_histogram, range, filters, nested
PipelineOperates on the output of other aggregations — moving averages, derivatives, bucket selection
Two results are approximate, and this genuinely surprises people. cardinality uses HyperLogLog++ — a distinct count that is close but not exact, in bounded memory. terms returns counts that may be slightly wrong, because each shard returns only its own top buckets and a term just outside one shard's cut-off is under-counted. The response reports doc_count_error_upper_bound, and it is almost universally ignored.
Raise shard_size above size when accuracy matters. Each shard then returns more candidates than you need, which shrinks the error at the cost of memory and transfer. Exact counts require either one shard or a different tool.
The mechanism, and the memory limits
  • Aggregations read doc_values — a columnar, on-disk structure held in the filesystem cache rather than on the heap. Enabled by default for non-text fields
  • Aggregating a text field requires fielddata, which is an on-heap structure and disabled by default for good reason. Aggregate .keyword instead — enabling fielddata to make an aggregation work is how nodes run out of heap
  • There is a cap on total buckets per request, defaulting to 65,536. A terms aggregation nested inside a date_histogram multiplies buckets and reaches it quickly
  • The cap is a protection, not an obstacle. Raising it to make a dashboard load moves the failure from a clear error to an out-of-memory event
For repeated aggregations over unchanging history, use a transform to pre-compute results into a summary index. Aggregating the same billion documents on every dashboard refresh is work that only needed doing once.
9  ·  CLUSTER & HIGH AVAILABILITY topology decisions
Getting the topology right
  • Three dedicated master-eligible nodes, in separate failure domains. They need little CPU or disk and they keep the cluster stable — a master that is also a busy data node is the classic cause of instability
  • At least one replica for every index you cannot afford to lose or to have unavailable
  • Dedicated coordinating nodes in front of heavy search or Kibana traffic, so result merging does not consume data-node heap
  • Shard allocation awareness so primary and replica never land in the same rack or zone. Without it, replicas are not protecting you from the failure you actually expect
  • Separate ingest and ML roles at scale, so a heavy pipeline cannot starve search
A yellow cluster is not an emergency; a red one is. Yellow means a replica is unassigned — everything works, redundancy is reduced. Red means a primary is unassigned and some data is unavailable right now. Alerting that treats them the same produces noise that hides the case that matters.
Watermarks — a common surprise
  • Low — no new shards allocated to that node
  • High — shards actively relocated away, which itself creates load
  • Flood stage — indices on that node are made read-only to protect the disk. Writes start failing and the block must be released manually after space is recovered
The flood-stage block is the one that causes confused incidents. Disk space is freed, the cluster looks healthy, and writes still fail — because the read-only block persists until it is explicitly removed. Alert on disk usage well before the low watermark.
Across regions
  • Never stretch one cluster across distant regions. Master election is latency-sensitive and a WAN blip becomes an instability event
  • Cross-cluster replication — a follower index replicates from a leader, for disaster recovery or local reads
  • Cross-cluster search queries several clusters without moving data
10  ·  LIFECYCLE & DATA TIERS where cost control lives
Time-series data — logs, metrics, events — is written once, queried heavily when new, and rarely afterwards. Index lifecycle management moves indices through tiers matched to that curve, so old data does not sit on expensive hardware.
TierHardware and role
HotActively written and queried. Fast local SSD or NVMe, the most expensive nodes
WarmNo longer written, still queried. Cheaper storage, often fewer replicas
ColdRarely queried. Can be backed by searchable snapshots, removing the need for a full local replica
FrozenQueried very rarely. Data stays in object storage and is fetched on demand — dramatically cheaper, and much slower
The phases of a policy
  • Rollover — start a new index at a size, age or document threshold. The foundation of the whole approach
  • Shrink — reduce the shard count once writing has stopped
  • Force merge — down to one segment, now safe because the index is read-only
  • Searchable snapshot — move the data to object storage while keeping it queryable
  • Delete — drop the whole index at end of retention
Deleting an index is nearly free; deleting documents is expensive. A delete_by_query marks every matched document and forces merges to reclaim the space. Dropping a whole index removes files. This is the strongest argument for time-based indices — retention becomes a file deletion rather than a large background job.
Use data streams for append-only time-series data. They wrap rollover, naming and backing-index management behind one name you write to, and are the current recommended approach — rather than hand-rolled date-suffixed index names and a cron job to delete them.
Component templates compose into index templates, so mappings and settings shared across many indices are defined once. Combined with data streams this makes a new data source a small configuration change rather than a new bespoke pipeline.
11  ·  SECURITY the defaults are not enough
An unsecured Elasticsearch on a reachable network is fully readable and writable by anyone who finds it. The API is HTTP and has no authentication until you enable it. Publicly exposed clusters have been a recurring, large-scale source of data breaches, and they are scanned for continuously.
The layers
NetworkBind to private interfaces. Never expose the HTTP port publicly, regardless of authentication. Firewall the transport port separately
TLSOn both the HTTP layer and the transport layer between nodes. Transport TLS is what stops an unauthorised node joining the cluster
AuthenticationNative realm, LDAP, Active Directory, SAML, OIDC, Kerberos, PKI — and API keys for services
AuthorisationRole-based, down to index and action. Built-in and custom roles
Field and document levelRestrict which fields a role sees, and which documents — the mechanism for multi-tenancy within one index
Audit loggingRecords access and changes. Required in most regulated environments
Practices worth insisting on
  • API keys per service, scoped and rotatable — not a shared superuser password in a configuration file
  • Least privilege: a dashboard needs read on specific indices, not cluster admin
  • Kibana is a separate attack surface and needs its own authentication and network controls
  • Disable dynamic scripting where it is not needed, and keep script access restricted
  • Encrypt snapshots at rest — the repository holds a full copy of everything
Field-level security is not a substitute for separate indices when tenants are genuinely untrusted. It is enforced correctly, and it puts one misconfigured role between one customer's data and another's. Weigh that against the operational cost of separation deliberately.
12  ·  MEMORY, THE JVM AND CIRCUIT BREAKERS STAFF the heap rule that is usually quoted slightly wrong, and why the other half of RAM matters more
Sizing the heap
No more than 50% of RAMThe rest is for the filesystem cache, which Lucene depends on completely
Stay below the compressed pointer threshold26 GB is safe on essentially all systems, and some can go to around 30 GB. Above it the JVM abandons compressed object pointers and effective capacity falls — more heap yields less usable memory
Xms = XmxAvoids resizing pauses. Set both to the same value
Lock memoryPrevent the heap from being swapped. A swapping node is catastrophically slow and looks like a network problem
The commonly repeated version of this rule is “50% of RAM, max 32 GB”, and it is imprecise. The threshold where compressed pointers stop applying sits below 32 GB, and the documented safe figure is 26 GB. A node configured with 32 GB of heap may be performing worse than the same node at 26 GB. Verify rather than assume — the node info API reports whether compressed pointers are in use, and the answer should be yes.
The half you did not give to the heap is doing the most work. Lucene reads its index files through the operating system's page cache, so the filesystem cache is what makes search fast. A node with 64 GB of RAM and 26 GB of heap has around 38 GB caching index data — and that is usually the better allocation. Raising the heap to 48 GB actively harms search performance.
Circuit breakers
Elasticsearch estimates the memory an operation will need and rejects it before allocation if it would breach a limit. A rejected request is far better than a node lost to an out-of-memory error, which takes its shards with it.
BreakerGuards against
ParentTotal across all breakers — the backstop
Field dataLoading text field data onto the heap. Usually triggered by aggregating a text field
RequestA single request's structures — most often a very large aggregation
In-flight requestsThe total size of requests being processed — oversized bulk bodies
Treat a tripped breaker as a diagnosis, not an obstacle. It names the query or the bulk request that would have taken the node down. Raising the limit removes the protection and leaves the cause in place; the fix is the aggregation, the field being aggregated, or the batch size.
Reading the memory picture
  • Heap sawtoothing between roughly 30% and 70% is healthy — allocation and collection working normally
  • Heap that stays above 85% means repeated full collections and long pauses. The node may be evicted from the cluster for being unresponsive
  • Long garbage-collection pauses are a leading indicator of instability — track pause duration, not just heap percentage
  • The most common causes: too many shards per node, aggregations over very high cardinality, deep pagination, and oversized bulk requests
13  ·  SNAPSHOTS & RECOVERY replicas are not a backup
Replicas protect against hardware failure and nothing else. A mistaken delete, a bad mapping change or a faulty ingest pipeline is replicated faithfully and instantly to every copy. Only a snapshot recovers from those — and they are the failures that actually happen.
How snapshots work
  • Incremental at the segment level. Because segments are immutable, a snapshot copies only segments not already in the repository — so after the first, subsequent snapshots are small and fast
  • The repository is external — object storage or a shared filesystem. It must be reachable by every data node
  • They do not block indexing; a snapshot is a consistent point in time without a write freeze
  • Restore is per index, and you can rename on restore — which makes recovering one index into a live cluster straightforward
  • Automate the schedule with a snapshot lifecycle policy, including retention
The parts people miss
  • Test a restore, and time it. An untested backup is a hypothesis, and restore duration is a number your recovery objective depends on
  • Keep the repository in a different failure domain from the cluster
  • Snapshot the cluster state too, so templates, ILM policies and roles come back with the data
  • Retention must be automated, or the repository grows until it becomes a cost problem nobody owns
  • Encrypt at rest — the repository is a complete copy of everything
The genuinely strong position: be able to rebuild from source. If the data can be re-indexed from a database or an event log, a total cluster loss is a slow day rather than a disaster. Snapshots then reduce recovery time instead of being the only thing standing between you and permanent loss — and that is a much better place to be.

What the client must get right
  • Always read and write through an alias or a data stream, never a concrete index name. This is what makes reindexing invisible to the application
  • Use the bulk API for ingest, and check every item in the response — a 200 does not mean every document was indexed
  • Retry rejections with exponential backoff. Rejection is backpressure, and treating it as a hard failure loses data
  • Set request timeouts, and keep them shorter than your user-facing budget
  • Use search_after with a point-in-time for paging beyond the first few pages
  • Put non-scoring conditions in filter — free performance
  • Request only the fields you need via source filtering; returning large documents you discard is pure cost
  • Use API keys per service, scoped to the indices that service touches
The alias habit is the highest-value one on this list. It costs nothing on day one and converts every future mapping change from an outage into a routine background reindex and an atomic swap.

4A single expensive query — deep paging or a huge aggregation taking down a node
5Raw indexing throughput — the ceiling people plan for, and the last one reached
Note the order. The limit designs are built around — documents per second — is last. The ones that cause real incidents are memory and shard hygiene, both of which are visible on a dashboard weeks in advance if anyone is looking.
Degradation
  • Cluster unavailable, used for search — the application should degrade to a database query or a cached result, not return an error page
  • Cluster unavailable, used for logging — buffer at the shipper and backfill. Never block the application on log delivery
  • Partial results — a search across many shards can return successfully with some shards failed. Check the shard failure count in the response, or you will silently show incomplete data

The one that summarises the sheet: state how large a shard is and how many exist, whether every field is explicitly mapped, whether applications read through an alias, and how long it would take to rebuild the cluster from source. Those four answers separate a search layer that can be operated and evolved from one that will need an outage to change — and the last is the question worth answering before an incident rather than during one.
