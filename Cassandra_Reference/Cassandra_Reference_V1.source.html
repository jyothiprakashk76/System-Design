1  ·  WHAT CASSANDRA IS — MASTERLESS, AP, AND OPTIMISED FOR WRITES start here — the three properties that make it excellent at a narrow thing and poor at everything else
The definition
A masterless, distributed, wide-column store. Every node is identical — there is no primary, no coordinator role that must be elected, and no single point of failure. Data is distributed by consistent hashing over a token ring, and replicated to a configurable number of nodes per data centre.
The design goal, stated once: linear write scalability and continuous availability across data centres. Doubling the nodes roughly doubles write throughput, and losing a node — or a whole region — does not stop writes. Everything awkward about Cassandra is the price of those two properties.
The three properties that explain everything else
1Writes never read first. A write is an append to a commit log and a memtable — no lookup, no read-modify-write, no locking. This is why writes are fast and uniform, and it is why a delete is itself a write (a tombstone), which causes most operational trouble
2There is no query planner and no join. You get exactly the queries your table was designed for. The data model is designed per query, and denormalisation is the intended practice rather than a compromise
3Consistency is a per-operation choice. It is AP by default, and the same cluster behaves closer to CP when you ask for quorum on both sides. See panel 5
Almost every Cassandra failure traces to one of those. Panels 2 and 9 cover the two that cause real incidents: a partition key chosen badly, and tombstones left unrepaired.
Where it sits on CAP
Cassandra is AP — during a partition, nodes on both sides keep accepting reads and writes at low consistency levels, and the cluster converges afterwards through read repair, hinted handoff and anti-entropy repair. Availability is preserved; a read may return stale data.
The nuance worth adding. Because consistency is tunable per operation, a write and a read that both use QUORUM give linearizable-per-key behaviour for that operation — at the cost of failing when a quorum is unreachable. Cassandra is not fixed at AP; the default is AP and you choose the position per statement. That is the most accurate answer to the question.
Use it when
  • Write volume is very high and continuous — event logs, clickstreams, sensor and telemetry data, time-series
  • Always-on across regions is a genuine requirement, with no failover window
  • Access is by a known key and the queries are stable and few
  • Linear scale-out is needed and adding nodes must not require re-architecting
  • Eventual consistency is acceptable for most reads
Do not use it when
  • Queries are ad-hoc or exploratory. You must know them before designing the tables — this is the hardest constraint to accept and the most commonly underestimated
  • The data is relational with joins across entities — there are no joins, and doing them in the application at scale is painful
  • You need multi-row or multi-table ACID transactions — see the note below
  • The workload is delete-heavy, or resembles a queue. Tombstones make this actively hostile
  • The dataset is small. A three-node minimum for meaningful replication is overkill for data that fits on one machine
  • Aggregations across partitions are needed — that is an analytics engine's job
The correction worth making early: lightweight transactions are not ACID transactions. An IF clause gives linearizable compare-and-set within a single partition, implemented with Paxos. It is not multi-row, not multi-table, has no rollback, and costs several round trips. Describing it as ACID sets an expectation the database cannot meet.
STAFF Version context. Cassandra 5.0 brought the most consequential changes in years: Storage-Attached Indexes, which fix much of what made secondary indexes unusable; a vector type with approximate-nearest-neighbour search combinable with normal CQL filters; the Unified Compaction Strategy, which subsumes the older strategies and self-tunes; trie-based memtables and the BTI SSTable format; and dynamic data masking. If you last evaluated Cassandra on 3.x, several conclusions are now out of date.
2  ·  DATA MODELLING — QUERY FIRST, AND THE PARTITION KEY DECISION the skill that separates a working cluster from a failing one · JUNIOR the keys · STAFF partition sizing
The governing rule, and it genuinely inverts relational practice: start from the queries, not the entities. Write down every query the application will make, then design one table per query, duplicating data freely. Normalising first and hoping the queries work out produces a data model that cannot serve them at all.
The primary key has two parts, and they do different jobs
PRIMARY KEY ( (user_id, day), event_time, event_id ) └──────┬──────┘ └────────┬─────────┘ PARTITION KEY CLUSTERING COLUMNS decides WHICH decide the ORDER node stores it WITHIN the partition
Partition keyHashed to a token, which determines the node. Every query must supply it — without it there is no way to know which node holds the data
Clustering columnsSort rows on disk within the partition. Range scans and ordering are efficient only along this order
Static columnsOne value shared by the whole partition
Design the sort order into the table. WITH CLUSTERING ORDER BY (event_time DESC) makes “most recent first” free — the rows are already stored that way. Sorting at query time in any other order is not available.
Denormalisation is the design, not a shortcut
  • The same data lives in several tables, each shaped for one query. This is correct and expected
  • The application maintains the copies. There is no join and no cascade — writing to all of them is your code's responsibility
  • Storage is cheap; a query that cannot be served is not
Partition sizing is where clusters are made or broken. A partition lives entirely on its replica nodes and is read as a unit. Keep partitions under roughly 100 MB and 100,000 rows as a working guide. Beyond that, reads slow, compaction struggles, repair takes longer, and memory pressure rises on exactly the nodes holding it.
The two ways a partition key goes wrong
Unbounded growthThe partition has no natural limit — all events for a device, forever. It grows until it breaks. The fix is bucketing: add a time component such as day or month to the partition key so each partition is bounded by construction
Hot partitionsOne key receives a disproportionate share of traffic — a status flag, a country, a popular tenant. Low cardinality is the warning sign. That partition's replicas are saturated while the rest of the cluster is idle, and adding nodes does not help
-- unbounded: grows forever PRIMARY KEY ( device_id, reading_time ) -- bounded: one partition per device per day PRIMARY KEY ( (device_id, day), reading_time ) -- hot: a handful of distinct values PRIMARY KEY ( status, order_id ) -- spread: add a bucket to widen the key PRIMARY KEY ( (status, bucket), order_id )
The trade with bucketing is query fan-out. Reading a month now means reading thirty partitions rather than one. That is usually the right trade — thirty bounded reads are far better than one unbounded partition — but choose the bucket size against the query, not arbitrarily.
The test to apply before committing to a key: how many distinct values does it have, how large can one partition become at full retention, and does every read supply it? If any answer is uncomfortable, change the model now — it is by far the most expensive thing to change later.
3  ·  ANTI-PATTERNS the ones that reliably cause incidents
Anti-patternWhy it fails
Using it as a queueThe classic. Insert, read the oldest, delete, repeat — every delete leaves a tombstone at the front of the partition, so each read scans through more and more of them until it times out. Cassandra is actively bad at this, and no tuning fixes it
Delete-heavy workloadsSame mechanism. Deletes are writes, and the space is only reclaimed after compaction and the grace period. Prefer TTLs, or partition so removal is dropping whole partitions
Read-modify-writeRead a value, modify it, write it back. Two concurrent clients silently lose one update — there is no locking. Use a lightweight transaction if you truly need it, and expect the cost
ALLOW FILTERINGIt does not enable a feature — it disables a safety check and permits a scan across nodes. Fine in an ad-hoc investigation, never in application code
Cross-partition batchesTreated as a performance optimisation when it is the opposite. See panel 10
Secondary indexes on high-cardinality columnsHistorically fans out to every node. See panel 11
Unbounded collectionsA list or map that keeps growing is read and rewritten whole. Keep them small and bounded, or use clustering rows instead
One giant table for everythingRelational instinct. One table per query is the model
The common thread. Every one of these is a relational or queue-shaped habit applied to a store that is optimised for a different access pattern. They usually work in development, where volumes are small and partitions are short, and fail months later in production once the data has accumulated.
The counter-question that catches most of them: “which partition does this query read, and how large will it be in a year?” If the answer is “several” or “we don't know”, the design needs another pass before it ships.

5  ·  CONSISTENCY LEVELS — WHAT EACH ONE ACTUALLY GUARANTEES MID the levels · STAFF the two that are routinely described wrongly
LevelRequires
ANY
write only		The write succeeds even if no replica received it — a hint stored on any node counts. The weakest level that exists; the data is unreadable until the hint replays. Almost never the right choice
ONEOne replica responds. This is the default for reads and writes unless the driver or session overrides it
LOCAL_ONEOne replica in the local data centre. Commonly the driver default in multi-DC deployments
TWO / THREEThat many replicas, anywhere
QUORUMA majority across all data centres. Correct but often unintended in a multi-DC cluster — it pays cross-region latency

Two corrections worth stating explicitly, because reference material gets both wrong.
1 · ANY is not “one replica”. That describes ONE. ANY succeeds when every replica is down, by storing a hint — the write is durable but not readable until replay.
2 · QUORUM is not the default. The default is ONE. A cluster where nobody set a consistency level is running at ONE, not at a balanced middle setting.
Apply R + W > RF to choose. With RF 3, the common production pairing is write LOCAL_QUORUM and read LOCAL_QUORUM — 2 + 2 > 3, consistent within the region, and tolerant of one node down. Drop either side to ONE and you have chosen speed over the guarantee, which is legitimate for metrics and logs and wrong for anything a user reads back immediately.
How divergence is repaired — three mechanisms
Hinted handoffThe coordinator stores writes for a briefly unavailable node and replays them. Bounded by a time window — beyond it, hints are dropped
Read repairDivergence found during a read is corrected on the spot. Only helps data that is actually read
Anti-entropy repairnodetool repair. The only mechanism that reaches every row. Not optional — see panel 9
Conflicts resolve by last-write-wins, per column, on timestamp. There is no merge and no conflict surface. Clock skew across nodes therefore causes silent data loss — a write with an earlier timestamp is discarded. Run NTP everywhere and monitor drift; this is not a theoretical concern.
6  ·  CQL & QUERY RULES SQL-like syntax, very different rules
CQL looks like SQL and is not SQL. There are no joins, no subqueries, no aggregates across partitions and no query planner. The syntax being familiar is the trap — what a query is allowed to do is determined entirely by the primary key of the table it reads.
What a WHERE clause may contain
  • The full partition key is required — always, with equality. Without it the cluster cannot know which node to ask
  • Clustering columns must be restricted in order — you cannot skip one. With (a, b, c), filtering on a and c is not allowed
  • Only the last restricted clustering column may use a range. Everything before it must be equality
  • ORDER BY can only follow the clustering order, forwards or reversed
  • Anything else requires ALLOW FILTERING, which is a warning rather than a feature
-- PRIMARY KEY ((user_id), event_time, event_id) OK WHERE user_id = ? OK WHERE user_id = ? AND event_time > ? OK WHERE user_id = ? AND event_time = ? AND event_id = ? NO WHERE event_time > ? -- no partition key NO WHERE user_id = ? AND event_id = ? -- skips a clustering col
These restrictions are a feature, not a limitation. The database refuses queries it cannot serve efficiently, rather than accepting them and degrading unpredictably at scale — which is what a relational database would do. ALLOW FILTERING switches that protection off, and it is the reason it should never appear in application code.
Other things worth knowing
  • TTL per row or column — data expires automatically. The best answer to deletion, since it avoids explicit tombstones from application logic
  • Counters live in their own tables and cannot mix with normal columns. They are not idempotent, so a retried increment may double-count
  • Collections — set, list and map. Keep them small; a non-frozen collection is read and rewritten as a unit
  • INSERT and UPDATE are the same operation — both are upserts. There is no “row does not exist” error
  • Paging is automatic in the drivers. Do not implement it manually with offsets
7  ·  STORAGE ENGINE — SSTABLES, CACHES AND WHY READS COST MORE THAN WRITES STAFF the log-structured design, and the read amplification that follows from it
Cassandra is a log-structured merge store. Writes append to memory and are periodically flushed to immutable files. Nothing is ever modified in place — which makes writes sequential and cheap, and makes reads a merge across however many files hold fragments of the row.
The components
Commit logAppend-only, per node. The durability guarantee — a crash replays it. Put it on separate storage from data if the disks are not fast
MemtableIn-memory, sorted, per table. Absorbs writes until flushed
SSTableImmutable sorted file on disk. Once written it is never modified — only merged away by compaction
Bloom filterPer SSTable. Answers “this key is definitely not here” without a disk read, so most SSTables are skipped. False positives cost a wasted lookup; false negatives cannot occur
Partition index
and summary		Locate a partition's offset within an SSTable
Key cacheCaches those offsets. Cheap and effective — usually worth increasing
Row cacheCaches whole rows. Off by default and usually correct to leave off — it is invalidated on any write to the partition, so it hurts mixed workloads
Rely on the operating system page cache. Cassandra reads SSTables through it, so unallocated memory is doing useful work. This is why heap should stay modest and the rest of RAM left free — raising the heap to consume the machine reduces the cache that makes reads fast.
Read amplification, and why it is the thing to watch
A single logical row can have fragments in the memtable and in many SSTables — one holding the original insert, another an updated column, another a tombstone. Every read must consult all of them and merge by timestamp.
So the number of SSTables a read touches is the read cost. Compaction exists to keep that number low. When compaction falls behind — because the strategy is wrong, or the node is I/O saturated — read latency degrades steadily with no change to the queries. The metric to watch is SSTables per read, and it is one of the most diagnostic numbers in the whole system.
Compression and disk
  • Compression is on by default — LZ4 is fast and usually correct. Chunk length trades ratio against read cost, so smaller chunks suit random reads
  • Local storage, not network-attached. Cassandra assumes fast local disks; putting SSTables on remote storage undermines the design
  • Leave real headroom. Compaction needs space to write merged output before removing inputs — a disk near capacity cannot compact, which increases read cost and fills the disk further
  • Never use RAID with parity for data. Cassandra replicates across nodes already; disk-level redundancy adds write cost for a guarantee you have elsewhere
The heap guidance. Keep the JVM heap moderate — commonly 8 to 16 GB with the modern collectors — and leave the rest of RAM to the page cache. Long garbage-collection pauses cause nodes to be marked down by their peers, which triggers hints, repairs and cascading load. Pause time matters more than heap size, and it is the metric to alert on.
8  ·  COMPACTION choosing the strategy correctly
Compaction merges SSTables, discarding superseded values and expired tombstones. It is what keeps reads fast and what reclaims disk. Choosing the wrong strategy is one of the most consequential and most reversible decisions here.
StrategyBehaviour and fit
STCS
size-tiered		Merges SSTables of similar size. Low write amplification, higher read amplification, and can need up to double the space during a large compaction. Suits write-heavy workloads with few overwrites
LCS
levelled		Maintains levels so a row appears in few SSTables. Excellent read performance and much higher write amplification. Suits read-heavy workloads with frequent updates — and will struggle if the write rate exceeds what it can compact
TWCS
time-windowed		The correct answer for time-series with TTLs. Groups data by time window so an entire window expires and is dropped as a unit, with no tombstone scanning at all
UCS
unified, 5.0		Subsumes the tiered and levelled behaviours behind one configurable strategy that adapts as the workload changes. The direction of travel, and it removes much of the guesswork above
The decision, in one line each. Time-series with a TTL → TWCS, and the benefit is large. Read-heavy with updates → LCS. Write-heavy, few updates → STCS. On 5.0, UCS unless you have a specific reason.
TWCS with explicit deletes defeats itself. Its advantage is that a whole window expires together. Deleting individual rows inside a window creates tombstones that prevent the window being dropped cleanly — so use TTLs, not DELETE, on TWCS tables.
Operating it
  • Watch pending compactions. A number that keeps climbing means compaction cannot keep up, and read latency will follow it
  • Throughput is throttled by default so compaction does not starve queries. Raising it helps a backlog and costs foreground latency
  • Never run a major compaction routinely — it produces one enormous SSTable that subsequent compactions cannot manage well, and the effect is long-lived
  • Changing strategy is safe but not instant — it rewrites data in the background
9  ·  TOMBSTONES & REPAIR the failure that defines Cassandra ops
A delete is a write. It cannot modify existing SSTables because they are immutable, so it writes a tombstone — a marker saying “this is deleted as of this timestamp”. The tombstone must be replicated everywhere, and it must outlive the data it hides.
Why a read gets slower after deletes
  • Tombstones are read like any other data. Scanning a partition means walking through them to determine what still exists
  • Thresholds exist and they fire. Passing a certain count per query logs a warning; passing a much higher one aborts the query outright
  • This is exactly why the queue pattern fails — the deleted head of the partition is scanned on every read, and grows
The critical rule, and the reason repair is mandatory. Tombstones are purged after gc_grace_seconds — ten days by default. If a node was down or missed the tombstone and it is purged elsewhere before that node learns of it, the deleted data comes back when the node rejoins. It is a real, silent correctness failure with a name: zombie data.
Therefore: nodetool repair must complete on every node within gc_grace_seconds. This is not a tuning suggestion — it is a correctness requirement of the delete mechanism. A cluster where repair has not run in two weeks with the default grace period may already have resurrected data, and nothing will report it.
Repair in practice
  • Schedule it — with Reaper, or the built-in scheduling in newer versions. Repair that depends on someone remembering does not happen
  • Subrange or incremental repair to keep each run manageable on large clusters
  • It is expensive — it streams data and competes with live traffic. Run it continuously at low intensity rather than as an occasional large job
  • Alert on time since last successful repair per node, against the grace period
Reducing gc_grace_seconds shortens the repair deadline proportionally. It is a legitimate choice for TTL-only tables where nothing is explicitly deleted — and dangerous if repair cannot reliably finish inside the shorter window.
10  ·  TRANSACTIONS & BATCHES both routinely misused
Lightweight transactions
INSERT INTO users (email, id) VALUES (?, ?) IF NOT EXISTS; UPDATE accounts SET balance = ? WHERE id = ? IF balance = ?; -- compare and set
What they are, precisely. Linearizable compare-and-set within a single partition, implemented with Paxos. They are not multi-row transactions, not multi-table, and there is no rollback. Two statements with IF are two independent transactions.
And they are expensive. Paxos requires several round trips among replicas rather than one — commonly quoted as roughly four — so an LWT can cost an order of magnitude more than a normal write. Contention on the same partition makes it worse, because rounds fail and retry.
Use them for genuine uniqueness and state-transition guards — claiming a username, moving an order from pending to paid exactly once. Do not use them on a hot path, and never as a general substitute for the transactions a relational database provides. If a design needs them frequently, Cassandra is likely the wrong choice for that part of the system.
Batches — the most misunderstood feature here
A batch is not a performance optimisation. It usually makes things slower. A logged batch spanning several partitions gives atomicity — all statements eventually apply — at the cost of writing a batch log to two additional nodes first, and forcing one coordinator to fan out to many replicas it does not own. The parallelism of independent writes is lost.
Single-partition batchGenuinely useful. All statements go to one set of replicas and are applied atomically and isolated. This is the good case
Multi-partition logged batchUse only when atomicity across partitions is a real requirement — for example keeping denormalised copies in step. Accept the cost knowingly
Multi-partition unlogged batchAlmost always wrong. No atomicity and coordinator overhead. Send concurrent individual writes instead
The rule: batch for atomicity, never for throughput. For throughput, issue many asynchronous single-row writes — that is what the architecture is built for, and it will be faster.
11  ·  INDEXES & VIEWS and what 5.0 changed
Secondary indexes — the historical problem
A classic secondary index is local to each node. Since the indexed value gives no information about which partition holds it, a query using one must be sent to every node in the data centre and the results merged. Cost grows with cluster size, so the query gets slower as you scale out — the opposite of what the rest of the system does.
  • Worst on high-cardinality columns such as an email address — nearly every node is asked and nearly all return nothing
  • Also bad on very low cardinality such as a boolean — the matching partitions are enormous
  • Reasonable only when the query also supplies the partition key, narrowing it to one node
STAFF Storage-Attached Indexes change this materially. Introduced in Cassandra 5.0, SAI attaches indexes to SSTables so they participate in compaction and repair automatically, supports multiple indexed columns far more efficiently, and handles numeric ranges and text matching. It is the mechanism behind vector search as well. It does not eliminate the scatter-gather characteristic, but it makes indexing a reasonable tool rather than one to avoid — and it is the main reason to revisit conclusions formed on 3.x.
The default answer remains a second table. If you need to query by another attribute, write a table keyed by that attribute and maintain both from the application. It is more code and it scales predictably — which is the trade Cassandra asks you to make everywhere.
Materialized views
Treat them as experimental, because they are. Server-maintained views were flagged as experimental after release owing to correctness problems — a view can drift out of sync with its base table and there is no supported way to detect or fix it short of rebuilding. They remain marked experimental and require explicitly enabling.
The recommended alternative is the manual one: maintain the second table from application code. It is more work and its failure modes are ones you can see, test and correct — rather than silent divergence you discover from a customer report.
12  ·  OPERATIONS — NODE LIFECYCLE, SCALING AND THE COMMANDS THAT MATTER MID running a cluster · STAFF the steps people skip and regret
Adding and removing nodes
Adding a nodeIt bootstraps by streaming the ranges it will own from existing nodes. Add one at a time and let each finish — parallel bootstraps cause range confusion and heavy streaming load
After adding: cleanupThe step most often forgotten. Existing nodes still hold data for ranges they no longer own. Until cleanup runs, disk usage does not fall and people conclude scaling out did not work
Removing a live nodedecommission — it streams its data to the new owners before leaving. Graceful
Removing a dead noderemovenode — the cluster restores replica counts from surviving copies. Follow with repair
Replacing a nodeStart the replacement with the replace-address flag so it assumes the dead node's ranges rather than joining as a new member
Scaling is linear and it is not instant. Bootstrapping streams real data over the network, and on a large cluster that is hours. Plan capacity ahead of need — adding nodes during an incident adds streaming load to an already struggling cluster.
Rolling restarts are routine and safe at RF 3 with quorum reads and writes — one node at a time, waiting for the cluster to report it fully up before continuing. Run nodetool drain before stopping a node so it flushes memtables and stops accepting writes cleanly.

13  ·  SECURITY & BACKUP defaults are wide open
Authentication and authorisation are disabled by default. A cluster started with stock settings accepts any client that can reach the port, with full privileges. Combined with the default administrative credentials, an exposed cluster is compromised quickly and routinely.
What to enable
  • Authentication — switch to the password authenticator, change the default superuser credentials, and raise the replication factor of the system authentication keyspace so logins survive a node loss
  • Authorisation — role-based, granted per keyspace and per table. Applications get read and write on what they use, nothing more
  • TLS on both channels — client-to-node and node-to-node. Inter-node encryption matters particularly across data centres
  • Network isolation — never expose the client or inter-node ports beyond the trusted network
  • Encryption at rest at the volume level, or via a distribution that provides it
  • Audit logging, available in modern versions, where compliance requires it
  • Dynamic data masking (5.0) obscures sensitive column values from roles without permission to see them
Backups
  • Snapshots are hard links to current SSTables — near-instant and initially free in space, but they prevent those files being deleted, so old snapshots quietly consume the disk. Clear them
  • Incremental backups hard-link each new SSTable as it is flushed
  • Copy snapshots off the node. On-node snapshots do not survive losing the node
  • Restoring requires the token layout to match, or a full refresh — practise it before you need it
Replication is not backup. A mistaken TRUNCATE or a bad deployment replicates immediately to every replica in every data centre. Only an off-cluster backup recovers from that — and an untested restore is a hypothesis.

Host settings matter too. Disable swap entirely, raise file descriptor limits, disable transparent huge pages, use fast local disks, and run NTP everywhere — clock skew causes silent data loss under last-write-wins.
What the driver must get right
  • Set the consistency level explicitly per statement. The default is ONE, and inheriting it by accident is how “we thought we had quorum” happens
  • Use a data-centre-aware load balancing policy, pinned to the local DC — otherwise queries cross regions for no reason
  • Use prepared statements. They are parsed once, and they let the driver route requests directly to a replica rather than to an arbitrary coordinator — a real latency saving
  • Enable token-aware routing, which is what makes that possible
  • Configure retry and speculative execution deliberately — and remember that non-idempotent statements must not be retried blindly, counters especially
  • Let the driver page result sets; never emulate offsets
  • Set timeouts shorter than the server's, so the client fails before the coordinator does
Token-aware routing with prepared statements is the single biggest client-side win. It removes one network hop from every request by sending it straight to a node that owns the data.

What breaks first
#Limit
1The data model. A hot or unbounded partition, or a query the tables cannot serve. By a wide margin the most common — and the most expensive to correct
2Tombstones and missed repairs — gradual degradation, then aborted queries or resurrected data
3Compaction falling behind, driving read amplification upward
4GC pauses marking nodes down and cascading load onto the rest
5Raw write throughput — the thing Cassandra is best at, and the last limit you reach
Note the order. The property people choose Cassandra for is the last to fail. The failures that actually occur are modelling decisions and maintenance discipline — both settled long before the cluster is under load.
Degradation
  • One node down at RF 3 — no impact at quorum. Hints accumulate and replay on return
  • Two nodes down at RF 3 — quorum operations fail for the ranges they share. Reads at ONE still work
  • A data centre unreachable — LOCAL_QUORUM continues normally, which is precisely why it is the default choice. EACH_QUORUM stops
  • A node down beyond the hint window — it returns with a gap that only repair will close

The one that summarises the sheet: name the partition key for every table, state how large the largest partition becomes at full retention, say when repair last completed on every node, and give the consistency level the application actually uses. Those four answers cover the failures that genuinely take Cassandra down — and none of them are about throughput, which is the one thing it will do well regardless.
