1  ·  WHAT POSTGRESQL IS — AND THE TWO ARCHITECTURAL FACTS THAT SHAPE EVERY OPERATIONAL PROBLEM start here — MVCC and the process-per-connection model explain almost everything else on this sheet
The definition
A fully ACID relational database with an unusually deep type system and an extension mechanism that lets it absorb workloads other databases exist to serve — geospatial, document, time-series, full-text and vector search. It is genuinely open source under the PostgreSQL Licence, with no commercial tier withheld from the core.
The reframe worth carrying into any design discussion. The question is rarely “PostgreSQL or a specialist database” on day one. It is “can PostgreSQL carry this until the scale genuinely demands something else?” — and the answer is yes far more often than architecture diagrams suggest. One database you operate well beats four you operate adequately.
The two facts that explain the operations
1MVCC: writes never modify a row in place. An update writes a new row version and marks the old one dead. Readers never block writers and writers never block readers — and the dead versions must later be reclaimed. Bloat, vacuum and transaction ID wraparound all follow from this one design choice
2One operating-system process per connection. Each carries real memory and startup cost, so a few thousand connections is not a configuration setting — it is a resource problem. This is why a connection pooler is not optional at scale
Nearly every PostgreSQL incident traces back to one of those two. Panels 2 and 8 cover them directly; most of the failure table in panel 15 is downstream of them.
Use it when
  • You need real ACID transactions and referential integrity — this is its core competence and it is very good at it
  • The data is relational, with joins and constraints that should be enforced by the database
  • Mixed workloads — relational tables alongside JSONB documents, geospatial data or vectors, all in one transaction
  • Correctness matters more than raw write throughput
  • You want one system to operate well rather than several specialised ones
Look elsewhere when
  • Write volume genuinely exceeds one primary and cannot be partitioned by tenant or key — PostgreSQL has no built-in sharding
  • Large-scale analytical scans over billions of rows — a columnar engine is the right tool, though extensions narrow this considerably
  • Sub-millisecond key-value lookups at very high rates — an in-memory store is a better fit in front of it
  • Full-text search at large scale with heavy relevance tuning — built-in search is capable, a dedicated search engine is more so
A note on the throughput ceiling. Figures like “switch away above N operations per second” circulate widely and are not meaningful — the real ceiling depends entirely on row size, index count, transaction shape and storage. Measure your workload; well-tuned PostgreSQL on modern hardware handles far more than most such rules of thumb suggest.
What it does not have, stated plainly
No built-in shardingHorizontal write scale needs application-level partitioning or an extension such as Citus
No automatic failover in coreReplication is built in; promoting a replica requires external tooling — Patroni, repmgr or pg_auto_failover. A cluster without one has no automatic failover, whatever the diagram says
No multi-master in coreLogical replication is one-directional. Bidirectional setups are possible and bring conflicts you must resolve yourself — this is not equivalent to multi-master, and treating it as such loses writes
No built-in connection poolingPgBouncer or an equivalent sits in front. See panel 8
STAFF Version context. PostgreSQL 18 was released in September 2025 and is the current major line. It brought a reworked asynchronous I/O subsystem with substantial read improvements, skip scans on multicolumn B-tree indexes, virtual generated columns, a native uuidv7(), OAuth 2.0 authentication, and faster major-version upgrades. Major releases arrive annually each September, and each is supported for five years.
Upgrades are worth planning as routine work. Each major version brings planner and performance improvements that are free once you take them, and running an unsupported version is a security position rather than a stability one.
2  ·  MVCC, VACUUM, BLOAT AND TRANSACTION ID WRAPAROUND the single most important operational topic · MID why bloat happens · STAFF the failure that stops the database
The mechanism. Every row version carries the transaction id that created it and the one that deleted it. An UPDATE writes a new version and marks the old one dead; a DELETE only marks it dead. Each transaction sees the versions valid for its snapshot. Readers never block writers, and writers never block readers — which is the great strength of the design.
The cost: dead row versions accumulate. They occupy space in the table and in every index on it, and they must be reclaimed. That reclamation is vacuum, and understanding when it cannot run is the difference between a database that stays healthy and one that quietly degrades for months.
What vacuum does
  • Reclaims dead tuples so the space is reusable — it does not return space to the operating system
  • Updates the visibility map, which is what makes index-only scans possible
  • Freezes old transaction ids, which is what prevents wraparound
  • Autovacuum runs it automatically, triggered by the proportion of a table that is dead
VACUUM FULL is a different operation entirely. It rewrites the whole table, genuinely returns space, and takes an ACCESS EXCLUSIVE lock for the duration — blocking all reads and writes. It is a last resort, not routine maintenance. pg_repack achieves a similar result without the long exclusive lock.
Reducing bloat at the source
  • HOT updates avoid touching indexes when no indexed column changes and the new version fits on the same page — a large win, and one reason to drop unused indexes
  • Lower fillfactor on heavily updated tables leaves room on each page for HOT updates
  • Batch large deletes, or use partitioning so removal is dropping a partition rather than deleting rows
Why autovacuum stops being able to clean — the thing to actually watch. Vacuum can only remove a row version once no transaction could still need to see it. Anything holding an old snapshot pins that horizon, and dead tuples accumulate across the entire database even though vacuum appears to be running normally.
The three things that hold the horizon back
Long-running transactionsIncluding a session sitting idle in transaction — an application that opened a transaction and went to lunch. The most common cause by far
Inactive replication slotsA slot for a replica that no longer exists pins the horizon and retains WAL indefinitely. See panel 7 — this fills disks
hot_standby_feedbackLets a replica's long queries hold back vacuum on the primary. It prevents query cancellations on the replica and this is the price
Set idle_in_transaction_session_timeout and statement_timeout. These two settings prevent the most common cause of unbounded bloat, and they cost nothing. Monitor the oldest transaction age continuously.
STAFF Transaction ID wraparound — the failure that stops the database. Transaction ids are a finite 32-bit space of about two billion. Old ids must be frozen by vacuum before the counter laps them. If freezing falls far enough behind, PostgreSQL issues escalating warnings and then refuses new write transactions entirely to avoid losing data — the database stops until an offline vacuum completes, which on a large table can take hours.
It is entirely preventable and it still happens. The causes are always the same: autovacuum disabled or throttled too aggressively, a very long transaction left open, an abandoned replication slot, or a table whose autovacuum settings were overridden and forgotten. Alert on the maximum age of any table's oldest unfrozen transaction, long before the database starts warning — by the time it does, the remaining margin is measured in hours of work.
3  ·  ISOLATION LEVELS three behaviours, not four
PostgreSQL accepts all four standard levels in syntax, but READ UNCOMMITTED behaves identically to READ COMMITTED — MVCC never exposes uncommitted data, so a dirty read is not possible at any level. There are three distinct behaviours, and knowing that is worth stating in an interview.
LevelWhat a transaction sees
Read Committed
the default		A fresh snapshot at the start of each statement. Two identical queries in one transaction can return different results if another transaction commits between them
Repeatable ReadOne snapshot for the whole transaction — true snapshot isolation. Consistent reads throughout, and a write conflict raises a serialization failure the application must retry
SerializableSnapshot isolation plus predicate locking to detect dependency cycles. Guarantees the result matches some serial execution, and aborts transactions that would not
The anomalies each one permits
AnomalyRCRRS
Dirty readnonono
Non-repeatable readyesnono
Phantom readyesnono
Write skewyesyesno
Write skew is the one that catches people. Two transactions each read a consistent state, each decide their write is safe, and both commit — leaving an invariant broken that neither violated alone. The classic case is two on-call engineers each checking that someone else is still on duty before removing themselves, and both succeeding. Repeatable Read does not prevent this. Only Serializable does.
If you use Serializable, you must handle retries. It will abort transactions with a serialization failure, and the application is expected to retry them. Code that treats that as a fatal error turns a correctness feature into an outage. The cost is real and usually smaller than expected — measure it rather than assuming.
The pragmatic middle ground is Read Committed with explicit SELECT ... FOR UPDATE on the rows an invariant depends on. That takes real row locks and is often simpler to reason about than raising the isolation level globally.

5  ·  INDEXES — THE TYPES, AND WHEN EACH IS THE RIGHT ANSWER JUNIOR B-tree covers most cases · MID the specialised types · STAFF what indexes cost
TypeBest for
B-tree
the default		Equality, ranges, sorting, uniqueness. Covers the large majority of needs. From PostgreSQL 18 it can also skip-scan a multicolumn index when a leading column is not constrained
GINValues containing multiple items — JSONB keys, arrays, full-text vectors, trigram search. Slower to update than B-tree; excellent for containment queries
GiSTGeometric and range types, nearest-neighbour search, and the basis for PostGIS indexing
SP-GiSTNon-balanced structures — quadtrees, radix trees. Useful for particular spatial and text-prefix patterns
BRINVery large tables with natural physical ordering, typically append-only time-series. Stores only min and max per block range, so it is minuscule compared with a B-tree — and useless if the data is not physically ordered
HashEquality only. Rarely the right answer over B-tree
The variants that matter more than the types
  • Multicolumn — column order matters. The index serves queries on a leading prefix of its columns
  • Partial — WHERE status = 'active'. Far smaller and cheaper when queries always carry that predicate
  • Expression — ON t (lower(email)), matching a query that filters the same way
  • Covering — INCLUDE (...) carries extra columns so a query can be answered from the index alone
  • Unique — a constraint that is enforced by an index
Indexes are not free, and the cost lands on writes. Every index must be updated on insert and delete, and on any update that touches its columns — or that cannot be performed as a HOT update. Each one also consumes cache and needs vacuuming. An unused index is a permanent tax on every write with no compensating benefit.
Find unused indexes with pg_stat_user_indexes. Scan counts near zero after a full business cycle means the index is not earning its cost. Drop them — but check replicas too, since a reporting replica may be the only user.
Index-only scans
The fastest read available: the query is answered from the index without touching the heap. It requires every requested column to be in the index and the page to be marked all-visible in the visibility map — which is maintained by vacuum. A poorly vacuumed table silently loses index-only scans, and the query gets slower with no change to the code.
Building and maintaining them safely
  • CREATE INDEX CONCURRENTLY in production. A plain CREATE INDEX takes a lock that blocks writes for the whole build
  • It is slower and can fail, leaving an invalid index behind that must be dropped and retried — check for these afterwards
  • REINDEX CONCURRENTLY rebuilds a bloated index without the long lock
  • Indexes bloat too, particularly under heavy updates — monitor size against table size
Before adding an index, check whether one already serves the query. A multicolumn index on (a, b) already handles queries on a, so adding a separate index on a adds write cost for nothing. Duplicated and overlapping indexes accumulate quietly over years.
6  ·  QUERY PLANNING & EXPLAIN how to diagnose a slow query
The planner is cost-based and driven by statistics. It estimates rows at each step and picks the cheapest plan. It has no memory of previous executions — so a plan changes when the statistics change, which is why a query can turn slow overnight with no deployment.
EXPLAIN (ANALYZE, BUFFERS) SELECT … -- ANALYZE actually runs it, giving real timings -- BUFFERS shows pages hit vs read from disk -- the key signal: Seq Scan on orders (cost=… rows=100) (actual … rows=840000) estimated ↑ actual ↑ -- a large gap means the statistics are wrong, -- and every choice above this node is suspect
Reading the plan nodes
Seq ScanReads the whole table. Correct for small tables or when returning most rows — not automatically a fault
Index ScanWalks the index, then fetches rows from the heap
Index Only ScanAnswered entirely from the index. The fastest case
Bitmap Heap ScanCollects matches from the index, then reads the heap in physical order. Efficient for medium-sized result sets
Nested LoopGood when one side is small; disastrous when the row estimate was wrong and it is actually large
Hash JoinBuilds a hash of one side. Needs work_mem, or it spills
Merge JoinBoth inputs sorted — good for large, already-ordered sets
The first thing to look for is not the slowest node — it is the largest gap between estimated and actual rows. The planner made every subsequent choice on that estimate. Fix the estimate, with ANALYZE, a higher statistics target, or extended statistics for correlated columns, and the plan often corrects itself.
work_mem is per sort or hash operation, not per query or per connection. One query with several sorts can use it several times over, and many concurrent connections multiply that again. Setting it globally high is a well-known route to running the machine out of memory — raise it for the specific session or query that needs it.
7  ·  REPLICATION, HIGH AVAILABILITY AND THE SLOT THAT FILLS YOUR DISK MID physical versus logical · STAFF what core does not provide, and the classic outage
Physical versus logical
Physical (streaming)Logical
ShipsRaw WAL — byte-level changesDecoded row changes
GranularityThe entire cluster, all or nothingPer table, via publications
VersionsMust matchCan differ — the basis of near-zero-downtime major upgrades
Replica writesRead-onlyWritable — which is what creates conflicts
Use forHigh availability, read replicas, disaster recoverySelective replication, upgrades, feeding other systems
Synchronous or asynchronous
  • Asynchronous is the default. The primary commits and replies before any replica has the change — so a failover can lose recently acknowledged writes
  • synchronous_commit controls how far a commit must get before returning. It can require a replica to have received, flushed, or applied the record — each stronger and slower than the last
  • Quorum commit allows “any two of these three”, which avoids one slow replica stalling all commits
  • Synchronous replication trades availability for durability: if the required replicas are unreachable, commits wait. Always configure more candidates than the quorum requires
The classic PostgreSQL outage: an inactive replication slot. A slot guarantees the primary retains WAL until the consumer has it — which is exactly what you want while the replica exists. When that replica is decommissioned, or a logical subscriber stops consuming, the slot remains and WAL accumulates without limit until the disk fills and the database stops. It is entirely silent until it is critical.
The prevention is three lines of monitoring. Alert on any slot where active is false, on the retained WAL size per slot, and on the WAL directory as a proportion of the volume. Set max_slot_wal_keep_size so a stuck slot is invalidated rather than allowed to take the primary down — losing a replica is much better than losing the primary.
High availability needs tooling
  • Core PostgreSQL will not promote a replica for you. Streaming replication gives a standby; something else must decide the primary is gone and act
  • Patroni with etcd or Consul is the common choice — quorum-based leader election with fencing to prevent two primaries
  • repmgr and pg_auto_failover are lighter alternatives with less coordination machinery
  • Clients must find the new primary — a virtual IP, a proxy such as HAProxy or PgBouncer, or multi-host connection strings with target session attributes
  • Test failover deliberately, including that the application reconnects and that the old primary cannot come back as a second writer
Replicas are not a backup. A mistaken DELETE or a bad migration replicates in milliseconds. Only backups with point-in-time recovery let you go back to just before the mistake — see panel 13.
8  ·  CONNECTIONS & POOLING not optional at scale
Each connection is a separate operating-system process with its own memory and scheduling cost. Idle connections still consume resources. This is why max_connections set to a large number is a symptom, not a solution — a database configured for a thousand direct connections will spend a large share of its time on context switching and lock contention rather than on queries.
The shape of the right answer: keep max_connections modest — commonly in the low hundreds — and put a pooler in front to multiplex many application connections onto few database ones. Applications open connections to the pooler, which is cheap; the database sees a small, steady number.
PgBouncer pool modes
ModeBehaviour
SessionA server connection is held for the client's whole session. Safest, least pooling benefit
TransactionReturned to the pool after each transaction. The usual production choice — very high multiplexing
StatementReturned after every statement. Multi-statement transactions are impossible
Transaction mode breaks anything that assumes a persistent session. Because a different backend may serve your next transaction: session-level SET, advisory locks, LISTEN/NOTIFY, WITH HOLD cursors and temporary tables all misbehave. Server-side prepared statements need matching support on both sides. These failures are intermittent and confusing precisely because they depend on which backend you land on.
Getting the sizing right
  • The database pool should be small — a common starting point relates it to CPU cores rather than to application instances
  • Application pools must sum to less than the pooler's limit, or connections queue in the wrong place
  • Set idle_in_transaction_session_timeout so a leaked transaction cannot hold a server connection and block vacuum
  • Reserve superuser connections so an administrator can still get in when the pool is exhausted
Connection exhaustion usually presents as a slow application, not a database error. Requests queue waiting for a connection while the database itself looks idle. Monitor pool wait time on the application side — the database will not tell you.
9  ·  DATA TYPES & JSONB the depth that distinguishes it
TypeNotes worth knowing
text / varcharNo performance difference in PostgreSQL. varchar(n) only adds a length check — use text unless the limit is a real business rule
numericExact decimal arithmetic. Use it for money; slower than floating point, and correct
timestamptzAlmost always the right choice over timestamp. It stores an absolute instant; the plain type stores a wall-clock reading with no time zone and quietly causes bugs
uuidNative 16-byte type. PostgreSQL 18 adds uuidv7(), which is time-ordered and therefore far better for index locality than random v4
jsonbBinary, indexable, deduplicates keys, does not preserve key order. Prefer it over json, which stores the original text and reparses on every access
arraysFirst-class, indexable with GIN. Useful, and not a substitute for a related table
rangesRanges of numbers or timestamps, with exclusion constraints that can prevent overlapping bookings declaratively
enum, domainConstrained values and reusable constrained types
Using JSONB well
  • Index it with GIN. The default operator class supports containment and key existence; jsonb_path_ops is smaller and faster for containment alone
  • Index a specific path with a B-tree expression index when queries always filter on the same field — much cheaper than a whole-document GIN index
  • Large documents get TOASTed, so retrieving them costs an extra fetch. Select the fields you need
The trap: JSONB used to avoid schema design. Fields that every row has, that are queried and constrained, belong in columns — where they get types, constraints, statistics and cheap indexes. JSONB is the right answer for genuinely variable, sparse or caller-defined structure, alongside proper columns for everything else.
The planner's statistics on JSONB contents are limited, so row estimates for containment predicates are weaker than for ordinary columns. That means worse plans on complex queries — another reason to promote heavily queried fields to real columns.
10  ·  PARTITIONING what it does and does not fix
Declarative partitioning splits one logical table into physical partitions by a key. The application queries the parent table and PostgreSQL routes reads and writes to the relevant partitions.
StrategyUse for
RangeThe common case — by date, for time-series data with retention
ListDiscrete values — region, tenant, category
HashEven distribution when no natural key exists
What it genuinely buys
  • Retention becomes DETACH or DROP of a partition — near-instant, and no bloat. Compare with deleting millions of rows, which creates dead tuples and demands vacuum
  • Partition pruning — queries filtering on the key skip irrelevant partitions entirely, at plan time or execution time
  • Maintenance operates per partition — vacuum, analyze and index builds work on manageable pieces
  • Bulk loading into a fresh partition, indexed afterwards and then attached
What it does not buy: it is not a general performance fix. A query that does not filter on the partition key must touch every partition, and is usually slower than it would have been against one table. Partitioning solves manageability and retention first, and query performance only for key-aligned access.
The constraints to plan around
  • Unique constraints must include the partition key — you cannot enforce global uniqueness on another column
  • Foreign keys referencing a partitioned table have historically been restricted; confirm behaviour for your version
  • Too many partitions costs planning time — thousands is a real burden. Match granularity to retention
  • Partitions must be created ahead of time — pg_partman or a scheduled job. A missing partition means failing inserts, usually at midnight
The signal that you need it is a large table where old data is dropped on a schedule, or where vacuum and index maintenance no longer complete in a sensible window. Partition then — not preemptively.
11  ·  LOCKING & SAFE MIGRATIONS how a schema change causes an outage
The mechanism that surprises people: locks queue, and a waiting lock blocks everything behind it. An ALTER TABLE needing an ACCESS EXCLUSIVE lock waits for a long-running query to finish — and every subsequent query on that table queues behind the waiting ALTER, including simple reads that would otherwise have been fine. A one-second schema change becomes a total outage on that table.
The defence is one line. Set lock_timeout before any DDL so the statement gives up quickly rather than accumulating a queue behind it. Retry in a loop if needed — failing fast repeatedly is far safer than waiting once.
-- the safe pattern for any production DDL SET lock_timeout = '3s'; ALTER TABLE orders ADD COLUMN note text; -- fails fast instead of queueing the world behind it
Operations and what they take
ADD COLUMN, nullable or with a constant defaultFast — metadata only since PostgreSQL 11. It does not rewrite the table
ADD COLUMN with a volatile defaultRewrites the whole table under an exclusive lock
Changing a column typeUsually a full rewrite. Prefer a new column, backfill, then swap
SET NOT NULLScans the table. Add a validated CHECK constraint first to make it cheap
Adding a foreign keyAdd it NOT VALID, then VALIDATE separately — the validation takes a much weaker lock
CREATE INDEXBlocks writes. Always use CONCURRENTLY in production
VACUUM FULLBlocks everything. Use pg_repack instead
Deadlocks are detected and resolved automatically — PostgreSQL aborts one transaction with a clear error. They are almost always caused by two code paths taking the same locks in different orders. Acquire locks in a consistent order and they largely disappear; the log names both statements involved.
12  ·  MEMORY AND CONFIGURATION — THE SETTINGS THAT ACTUALLY MATTER STAFF what each one does, and the one that is per-operation rather than per-server

work_mem is the setting most often misunderstood, and it is worth being precise about. It is the limit for each individual sort, hash or similar operation. A single query with several sorts and a hash join can allocate it several times over, and every concurrent connection does the same independently. Total consumption is roughly work_mem × operations × connections — which is how a value that looked reasonable takes a machine out of memory under load.
The safe approach: keep the global value conservative and raise it for the specific session, role or query that genuinely needs it. A reporting job can set it high for itself without putting the whole server at risk.
Settings worth setting on day one
  • statement_timeout — no query should run forever. Set it per role, higher for reporting than for the application
  • idle_in_transaction_session_timeout — prevents the most common cause of unbounded bloat
  • lock_timeout — set before DDL so a schema change cannot queue the world behind it
  • log_min_duration_statement — log slow queries. The cheapest observability available
  • log_checkpoints, log_lock_waits, log_autovacuum_min_duration — each turns a silent problem into a log line
  • shared_preload_libraries = 'pg_stat_statements' — requires a restart, so do it before you need it
Host settings matter too. Configure huge pages for large shared buffers, tune the kernel's dirty-page thresholds so checkpoints do not collide with the operating system's own flushing, and disable the OOM killer's attention on the postmaster — if it kills that process, the whole cluster restarts.
13  ·  SECURITY & BACKUP and the difference between them
Access control
  • pg_hba.conf is the first gate — it decides who may connect, from where, and how. It is evaluated top to bottom, first match wins, and it is where accidental trust entries hide
  • Use scram-sha-256, not the older md5 method
  • Roles, not users — grant to group roles and make people and services members
  • Never let the application connect as a superuser or as the table owner. The owner can drop the tables; the application only needs to read and write them
  • Row-level security enforces per-row visibility in the database — the mechanism for real multi-tenancy
  • TLS for all connections, and verify the certificate on the client rather than merely enabling encryption
  • Revoke the default public schema rights on new databases
Backups — three distinct things
pg_dumpLogical. Portable across versions and architectures, restores selected objects, and is slow to restore at large sizes
pg_basebackupPhysical. A byte-level copy of the cluster — fast to restore, tied to the version
PITRA physical base backup plus continuously archived WAL, allowing recovery to any moment. The only thing that undoes a bad migration at 14:32
Replication is not backup. It faithfully copies your mistakes. Point-in-time recovery is what lets you go back to just before one — and it is the difference between an incident and a catastrophe.
Use pgBackRest or barman rather than hand-rolled scripts. They handle parallelism, compression, retention, encryption and — importantly — verification. Then restore from them on a schedule and time it: an untested backup is a hypothesis, and restore duration is the number your recovery objective actually depends on.

What breaks first
#Limit
1A missing index or a bad plan. The most common cause of a sudden incident, and the cheapest to fix
2Bloat from a blocked vacuum — gradual, then sudden, and always traceable to a held snapshot
3Connection exhaustion, which presents as application slowness rather than a database error
4Lock contention, usually from a schema change meeting a long query
5Single-primary write throughput — the ceiling people plan for, and the last one reached
Note the order. Write throughput is last. The failures that actually occur are a query plan, a held transaction and a connection pool — all visible in advance, and all fixable without new hardware.
Degradation
  • Primary down without failover tooling — a full outage until someone promotes a replica. This is the argument for Patroni
  • Replica down — read capacity reduced; ensure the application falls back to the primary rather than failing
  • Failover with asynchronous replication — recent acknowledged writes may be lost. Decide whether that is acceptable, or run synchronously and accept the latency
  • Disk full — PostgreSQL stops writes to protect itself. Keep headroom, and alert on the WAL directory separately from the data directory
